# 重试要带上次的拒绝理由

> **失败形状**：系统给了第二次机会，却没告诉执行者第一次为什么失败，
> 于是第二次把同一份东西原样再交一遍，预算烧完、终局判死。
>
> 这比「没有重试」更坏：它消耗成本、制造「已尽力」的外观，成功率却接近零。

## 实测形状（离线全绿，真实三次会话全挂）

某轮候选离线 11306 项测试全绿，真实自然会话 3 次 0 交付。把 ledger 事件拉平后形状是确定的：

| seq | 事件 | 内容 |
|----|------|------|
| 7 | invalid_action | `not_json_object` |
| 8 | model_input | 回灌（**只回灌了第一次失败**） |
| 12 | invalid_action | `claim rendering requires one sentence per claim` |
| 15 | repair_goal | 只写了「缺哪几个输出」 |
| — | invalid_action | **同一个错误再犯** → 终局失败 |

三条独立病灶，同一个根：

1. **最后一次失败只落账、没送达**。loop 出于防重复/省调用，只在首次失败回灌；
   而**最后一次失败恰恰是离终局最近、最具体的那一条**。
2. **错误消息没有坐标**。「需要一句一条」不告诉作者是哪个输出的第几条、切成了几句，
   它只能猜——猜错就再犯。
3. **最后一次机会不重述合同**。修复轮只讲「缺什么」，不重述它仍然要求的格式；
   执行者得靠回忆开场约定，一旦内容改对、格式失手，直接终局。

## 可迁移规则

- **失败原因跟着重试走**：谁动手，谁就得拿到上一次的拒绝理由。给「协调者」看没有用。
- **只补没送达过的那一条**，不是「每次失败都回灌」——否则失败次数直接变成调用次数与死循环风险。
  实现上是一个纯函数：扫账本，失败置位、送达清零，剩下的就是欠账。
- **错误消息带病灶坐标**：`output.claims[1] has 2 sentences` 这种「哪一处、错成什么样」，
  而不是「不符合规范」。坐标从校验点产生，不要让上层去二次解析错误文本。
- **最后一次机会要把合同一并重述**，且与开场**共用同一个构造点**（两处各写一份，迟早漂移）。
- **不许为此放宽约束**。这类现场很容易被误诊成「规则太严」——规则没错，错的是反馈链。
- **分开两类信号**：给人/模型读的解释（原句 + 理由）与参与路由判定的策略字段要分开，
  否则「让作者看懂」的改动会顺手改掉「系统怎么处置」。
- **清零集合要包含你自己新开的送达通道，置位集合要按失败类别过滤**：扫账本找欠账是两个集合的问题。
  2026-09-17 QC 四向探测发现首版（8f6e6eaa）只认 `steering_invalid_finish` 为送达、又把任何
  `invalid_action` 都当终局拒收——max 档三轮修复里第二轮会把第一轮已送达、作者已改对的那条再发一遍；
  计划错误也会被套进 invalid_finish 文案。修法（04d3c397）：按结构化 `code`（rejection_code）置位、
  把 `repair_last_rejection` 计入清零，emit 点零改动。审这类函数至少探四向：已回灌一次、最后一次未回灌、
  **自己送达后进下一轮**、**同类失败经别的通道回灌**；第一轮看起来完美正是这个坑的外壳。

## 验证方式（不是靠离线绿）

修完后要在真实环境造出那个分支才算数。实测证据是同一形状的三次 run：

- 修前 `c6151407`、`8f6e6eaa`：修复轮原样重发 → `invalid_repair_finish`。
- 修后 `d8ba0fb2`：坐标错误 → 首次回灌 → 同错再犯 → **补发尾次拒绝**（135 字）
  → 修复目标消息 1689 字（**含重述的冻结格式**）→ `completed / repair_model_finish`。

离线 11318 项全绿只证明「没打碎别的」；**证明修好的是那条真实 run 的事件序列**。

## 边界

这条规则解决「执行者听不见」，不解决「裁判不稳定」。同一次复验里，
修复稿被接受之后，审查侧返回了一个非法回执 → 判官不可用 → 用户仍然什么都没拿到。
反馈链修好不等于交付成功，两者要分开记账。
