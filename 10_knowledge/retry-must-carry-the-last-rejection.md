# 重试要带上次的拒绝理由

> **失败形状**：系统给了第二次机会，却没告诉执行者第一次为什么失败，
> 于是第二次把同一份东西原样再交一遍，预算烧完、终局判死。
>
> 这比「没有重试」更坏：它消耗成本、制造「已尽力」的外观，成功率却接近零。

## 实测形状（离线全绿，真实三次会话全挂）

某轮候选离线 11306 项测试全绿，真实自然会话 3 次 0 交付。把 ledger 事件拉平后形状是确定的：

| seq | 事件 | 内容 |
|----|------|------|
| 7 | invalid_action | `not_json_object` |
| 8 | model_input | 回灌（**只回灌了第一次失败**） |
| 12 | invalid_action | `claim rendering requires one sentence per claim` |
| 15 | repair_goal | 只写了「缺哪几个输出」 |
| — | invalid_action | **同一个错误再犯** → 终局失败 |

三条独立病灶，同一个根：

1. **最后一次失败只落账、没送达**。loop 出于防重复/省调用，只在首次失败回灌；
   而**最后一次失败恰恰是离终局最近、最具体的那一条**。
2. **错误消息没有坐标**。「需要一句一条」不告诉作者是哪个输出的第几条、切成了几句，
   它只能猜——猜错就再犯。
3. **最后一次机会不重述合同**。修复轮只讲「缺什么」，不重述它仍然要求的格式；
   执行者得靠回忆开场约定，一旦内容改对、格式失手，直接终局。

## 可迁移规则

- **失败原因跟着重试走**：谁动手，谁就得拿到上一次的拒绝理由。给「协调者」看没有用。
- **只补没送达过的那一条**，不是「每次失败都回灌」——否则失败次数直接变成调用次数与死循环风险。
  实现上是一个纯函数：扫账本，失败置位、送达清零，剩下的就是欠账。
- **错误消息带病灶坐标**：`output.claims[1] has 2 sentences` 这种「哪一处、错成什么样」，
  而不是「不符合规范」。坐标从校验点产生，不要让上层去二次解析错误文本。
- **最后一次机会要把合同一并重述**，且与开场**共用同一个构造点**（两处各写一份，迟早漂移）。
- **不许为此放宽约束**。这类现场很容易被误诊成「规则太严」——规则没错，错的是反馈链。
- **分开两类信号**：给人/模型读的解释（原句 + 理由）与参与路由判定的策略字段要分开，
  否则「让作者看懂」的改动会顺手改掉「系统怎么处置」。
- **清零集合要包含你自己新开的送达通道，置位集合要按失败类别过滤**：扫账本找欠账是两个集合的问题。
  2026-09-17 QC 四向探测发现首版（8f6e6eaa）只认 `steering_invalid_finish` 为送达、又把任何
  `invalid_action` 都当终局拒收——max 档三轮修复里第二轮会把第一轮已送达、作者已改对的那条再发一遍；
  计划错误也会被套进 invalid_finish 文案。修法（04d3c397）：按结构化 `code`（rejection_code）置位、
  把 `repair_last_rejection` 计入清零，emit 点零改动。审这类函数至少探四向：已回灌一次、最后一次未回灌、
  **自己送达后进下一轮**、**同类失败经别的通道回灌**；第一轮看起来完美正是这个坑的外壳。

## 验证方式（不是靠离线绿）

修完后要在真实环境造出那个分支才算数。实测证据是同一形状的三次 run：

- 修前 `c6151407`、`8f6e6eaa`：修复轮原样重发 → `invalid_repair_finish`。
- 修后 `d8ba0fb2`：坐标错误 → 首次回灌 → 同错再犯 → **补发尾次拒绝**（135 字）
  → 修复目标消息 1689 字（**含重述的冻结格式**）→ `completed / repair_model_finish`。

离线 11318 项全绿只证明「没打碎别的」；**证明修好的是那条真实 run 的事件序列**。

## 内容门不能把纠错理由一起吞掉（2026-09-18补充）

finance 历史研究实录中，`stage_day` 被模型放进 metrics，校验器已生成「应为 dimension」的重试提示，但严格日期门看见 `evidence=[]` 就把整段观察替换为「未取得有日期材料」。拒绝理由在源头存在，仍没到达执行者。

候选 `a05b3483` 将可信程序诊断与事实分型：字段角色/超时/取消等由受审定生产者构造 `ToolDiagnostic`，经过白名单和标识符清洗，在事实过滤后交付；不生成可引用证据、不扩日期授权。**不能以错误状态或空证据直接豁免整段文字，也不能将原始外部异常改贴“诊断”后放行。** 混合结果只保留范围内事实和可信诊断，不恢复被过滤的原 prose。

这适用于日期、权限、租户隔离、隐私等内容门：同时测「该挡的仍挡」和「执行者能收到修复坐标」。本次临时数据库的脚本化真实 Episode 已验证拒绝→送达→改参→成功取数，四个进程内变异能被抓住；**没有因此复验真模型，原四题业务失败结论不变**。项目证据看 finance 分支的 `tests/test_history_tool_diagnostics.py`、`tests/test_history_argument_repair.py` 和 `scripts/review_probes/history_diagnostic_mutations.py`，不是通用过滤器已获全面认证。

## 先认对失败所属的输出类型（2026-09-21补充）

另一类失败不是理由没送到，而是**送错了修复合同**：finance 的 K3 写手返回完整研究计划，
只漏 `kind=PLAN`。候选识别器因此回答“不是计划”，终局门报缺 status，系统回灌
“只输出最终答案”，模型尚未取数就以无证据 partial 收尾。本地有数，但这一轮没读。

可迁移规则：纠错应保留原工作类型与阶段，不能把协议格式错自动升级为“工作该结束”。
若能以窄结构签名识别候选，就交给对应的严格校验器产生错误；**识别候选不等于接纳**。
不能为恢复流程而偷偷补授权字段/执行动作；终局字段、已收口状态和原有次数/预算仍优先。
无法明确分类的片段不猜。不选择“加重开场提示词”代替错误分流，也不全局放宽解析。

本次 `4c33e0d45` 只给“完整计划体缺标签、无终局字段”回原一次 PLAN 纠错；逐字节真实前缀、
脚本化续轮和四种撤保护验证分流/提示有效。后续工具与答案是离线替身，**未证明 K3 在修后
提示下会自然继续研究**。原件及断言见 finance 的 `test_research_plan.py`、`test_agent_episode.py`
与 `docs/handoffs/2026-09-21-adaptive-k3-plan-routing.md`。

## 可恢复错误不能遮住来源违规（2026-09-29补充）

拒收类别会决定是否调用下一稿，因此也是控制逻辑的一部分。延后某项格式错误时，不能先构造一个已知不完整的中间对象，让它抛出的普通异常抢在已发现的来源违规之前。核验应保留原始错误，继续检查仍可解析的来源；当前稿必须拒收，不能用删除引用或补缺口修成合法稿。

finance 的 Pi 接续候选中，未知 E9 被延后并删去后，空证据绑定的构造异常遮住同稿伪来源，两条研究循环均可再叫一稿。`d9eeb69b7` 保留未知引用错误、跳过无待查来源的临时对象，恢复完整性硬拒；正反顺序、空白引用、两循环反例先红后绿。相反，同一已知历史来源的多段摘录可给作者原预算内的格式重写机会，仍须交回单摘录终稿；未知或跨历史来源不能借此恢复。

可迁移到所有按异常类型选择重试的流程：同时测单错和混合错，检查最终动作及调用次数，不只断言抛异常。该结论覆盖具名边界，不声称任意不可解析输入都有全局错误优先级。真实历史首发另有一次成功，但未进入修复分支，不能冒充修复分支的自然模型证据。详情见金融仓 `docs/verification/2026-09-29-pi-continuation-review.md`。

## 边界

这条规则解决「执行者听不见」，不解决「裁判不稳定」。同一次复验里，
修复稿被接受之后，审查侧返回了一个非法回执 → 判官不可用 → 用户仍然什么都没拿到。
反馈链修好不等于交付成功，两者要分开记账。
