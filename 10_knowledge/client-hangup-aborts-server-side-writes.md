# 客户端超时不是旁观：挂断会把服务端的写杀在半路

> **失败形状**：客户端给写请求设了一个「平时够用」的超时。服务端一慢，客户端到点挂断，以为只是没拿到回答。实际上服务端框架把请求上下文绑在这次操作上，挂断即取消，写操作死在半路：有时什么都没落，有时底层状态已经改了、上层记录没跟上（半截状态）。

## 实例（Gitea，Go 的请求上下文）

- #959：合并 POST 在服务端 30282 ms 处返回 500。`git push` 在客户端 30 s 挂断的那一刻被杀，main 没动。
- #854：服务端共 51.7 s。挂断后 push 又跑了约 20 s，ref 更新了，但「把 PR 标成 merged」那一步没跟上：main 前进了，PR 仍是 open。
- 开 PR：日志里成簇的「201 in 30.0s」同一秒伴随一串 `context canceled`。PR 行已经写入，后续通知被取消。这些「30.0 s」是被客户端截断的读数，不是真实耗时。

## 规则

1. **超时按服务端最慢一次定：量日志，不拍脑袋。** 等得久的代价只在服务端真慢时才付；挂断的代价是半截状态，两边不对称。
2. **写请求报错 = 结果未知，不是失败。** 结果有三态：成了 / 没成 / 不知道。「不知道」要有自己的退出码或状态，别折进「失败」，否则调用方会去重试。
3. **只认回读，且分层读。** 对象状态（PR 的 `merged`）与底层真相（base ref）分开读：半截状态恰恰就是这两层对不上。
4. **从不自动重发非幂等的写。** 要重试，先回读，并带上身份条件（`--expect-head/--expect-base` 这类乐观并发条件），或者用幂等键。
5. **测试打在传输层**（假 urlopen / 假 HTTP 服务）。缺陷常在「封装层只转一种异常、调用方只接一种异常」的缝里，换掉封装层的测试看不见这条缝。

## 迁移

- 任何带请求作用域上下文的服务端框架：Go（`r.Context()`）、ASP.NET（`RequestAborted`）、Node（`req.on('close')` 后主动 abort）……客户端挂断都可能取消服务端正在做的事。
- 支付 / 下单 API 对同一问题的工业答案是**幂等键**（Idempotency-Key）：超时后带同一个键重发，服务端直接返回第一次的结果，而不是再做一遍。
- 数据库：客户端断开会回滚未提交的事务，但已经发生的外部副作用（发出的消息、写出的文件）不会跟着回滚。

## 面试怎么讲

- 「超时后能不能重试？」先问操作是否幂等。不幂等就回读，或用幂等键。这是「两将军问题」的工程版：仅凭「没收到回复」，永远判断不了对方做没做。
- 「超时设多少？」看服务端延迟分布的尾部（p99 / 最大值），不看平均值；还要说清挂断本身的代价。
