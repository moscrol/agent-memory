# Agent 系统第一性原理：从输入-处理-输出到精密闭环

## 结论 / 要点

1. **三段式（输入→处理→输出）是对的骨架，但只是前馈模型**。它能保证"流程走完"，不能保证"质量收敛"。缺两个一等公民：**评估/反馈** 和 **记忆/沉淀**。
2. 第一性原理：任何 LLM 系统都是一条**有损信息信道**（用户意图 → 上下文 → 模型 → 答案），每个节点的优化目标是提高信噪比、减少信息损失。
3. **优化的前提是可测量**。没有度量（answer-score、eval cases），对任何节点的调优都是盲调。评估必须和输入/处理/输出平级。
4. **输出不是终点**：最有价值的输出是会变成未来输入的部分（回写知识层、entity delta、经验卡片）。真实拓扑是环，不是线：

   ```
   输入 → 处理 → 质检 → 输出 → 评估 → 沉淀(记忆) ─┐
     ↑ ______________________________________________│
   ```

   单次会话是流水线，系统整体是闭环。
5. 控制论视角（可迁移到任何垂直 Agent）：**开环系统靠元件精度，闭环系统靠反馈**，后者对单个元件的误差不敏感。流程可控稳定的来源不是每个节点各自更好，而是环路收敛。

## 各节点的关键取舍

### 输入
- **ingest 结构化 = schema-on-write**，方向对，但要警惕源头过度结构化造成信息损失。对冲手段：`raw/` 不可变原文保留 schema-on-read 退路（知识库仓已实践）。
- **提示词措辞的杠杆很低且脆**；高杠杆的是结构化问题解析（QuestionPlan：规则先解析出任务类型 + 深度 + 视角 + 证据计划），把"让 LLM 猜意图"变成确定性编排。
- **context 工程本质是输入问题而非处理问题**：决定"给模型看什么"（检索质量）比"怎么跟模型说"（prompt 措辞）重要一个量级。

### 处理
- 两条正交的轴：
  1. **确定性轴**：能用规则的绝不用 LLM（路由、门控、字段校验），LLM 只留给必须的理解和表达——"规则编排 + LLM 生成"混合路线的本质是**用确定性组件压方差**。
  2. **质检独立成节点**：质检视角（影子用户反驳、审视者）与生成是对抗关系，混在生成里会退化成自我确认。

### 输出
- 分两类：**面向人的输出**（叙事编排，"rubric 防漏项，composer 防模板化"）和**面向系统的输出**（回写、沉淀、经验卡）。后者是闭环的回路，漏掉它系统就退化为开环。

### 评估 / 沉淀
- 事实库回答"世界发生了什么"，经验层回答"下次应该怎么想"，两者分开存放避免污染检索（见 [[finance-agent-experience-cards]]）。
- 最小闭环：回答 → 打分 → 低分/高价值样本存卡 → 下次合成时注入 → 多次验证后升级为稳定方法论。

## 2026-09-20 实测：回路必须跨过协议边界

金融研究候选 `feat/adaptive-research-loop@469ba766` 的 K3 原始记录在 `~/.finance-runtime/adaptive-research-20260920/`。三组双臂先后暴露：反馈可见但模型不提交计划；有计划却因 JSON 代码框被拒收；修正字段约束后又因普通尾部说明被拒收。修复后单臂接收五个自选视角并回传，但只有一次计划，没有证明新观察导致视角修订或答案更好。

可迁移的验证顺序：**指令可见 → 模型采取动作 → 解析接收 → 状态回传 → 实际研究改变 → 交付质量改善**。上游一格成立不能替后面几格签字。闭环也可发生在单次会话内，不应将其概括成必然的流水线；是否形成有效闭环必须靠行为证据。

结构化字段、权限和预算须严格；JSON 外包装的兼容性应单独测试，不要把无歧义的格式差异误当成领域判断失败。边界要明确：普通尾部说明可忽略，多个结构化值、前置说明或越权字段仍拒绝。字段上限还必须真实送给模型，只有解析器知道约束会浪费纠错轮次。计划数、工具数和更多证据都不是质量得分。

## 2026-09-21：约束回传与审查输入保真

续验原件 `~/.finance-runtime/adaptive-holdouts-20260920/`，解释与版本边界见 `finance-worktrees/adaptive-research-loop/docs/handoffs/2026-09-21-adaptive-research-holdouts.md`。四题八次同版本真实会话仍未证明质量提升；后续冻结前缀只验证协议，不是研究重跑。

- **校验规则要进入反馈输入。** 模型会把原输出项换成近义表达、遗漏旧分支目标，导致有价值的修订也不能落账。应从已接收状态派生精确保留项，而非放松校验或替模型暗补字段。可变判断与不可丢承诺分开。
- **允许结束也是闭环的一部分。** 证据足够的单一事实不应为解释空视角而被迫造计划；直接结束仍要走原证据与终态校验。返回收口对象没有证明计划修订，也没有证明语义正确。
- **版本号不是行为证据。** 第一次接收即标 revision=2，不能当作经历了两次有效计划。要对照连续接收状态及新观察、行动和交付，而不是看数字大小。
- **审查包必须保留空结果与失败。** 工具查过但没有证据条目，不等于没查过。只给 E 列表会让审查模型把真实查询误判为编造；反过来空结果也不能证明对象不存在。审查输入保真先于加审查模型数量。
- **材料授权不能靠工具名称或模型自觉。** “只用本地”样本的两臂都调用了联网财报路径。只读、联网与材料范围是不同属性；是否允许读取该来源要在执行边界核验，事后写 gaps 不会追认授权。

这些是由失败形状得到的验证纪律，不是本候选已具备全部控制的声明。默认开关仍关，材料授权与公开稿保真问题未在本片修复。

## 2026-09-21 续修：权限第一步与查询身份

`feat/adaptive-research-loop@b6df991f` 复现“只用本地已有资料”未编出材料合同，已有执行闸因此拿到默认读取权限。补丁只补共用分类器的明确来源句式，沿用既有执行上限；旧材料限制不放宽，引用/否定/题内歧义仍分别隔离或澄清。**验证授权要从原始用户表达穿到执行前拒绝**，只对手工造好的受限合同测闸门，会漏掉第一步。

审查器 `03c08f48` 保留 request/result/error（含空观察）、稿件各阶段与原交付。续查发现运行时判官按 capability/status/result_count/date 合并空查询，会把监管、行情、核心股三次不同查询压成一条。**压缩的去重键必须保留当前判断所需的身份**；相同工具、零结果不等于同一次查询。缺少身份不能推断“没查过”，查过为空也不能推断“没有风险”。这是已定位的后续修复项，不代表运行时投影已经修好。

## 背景 / 依据

- 用户提出：本质上一直在重复"输入、处理、输出"，提高每个节点的效率和质量即可让流程可控稳定。
- 审阅确认三个仓库已有对应实践：ingest 结构化（frontmatter + relations JSON）、QuestionPlan 编排层、L3 证据运行时补查、影子用户反驳质检、narrative composer、experience cards——但"评估驱动沉淀、沉淀改善输入"的闭环尚未被提到节点高度、也未完全自动化。
