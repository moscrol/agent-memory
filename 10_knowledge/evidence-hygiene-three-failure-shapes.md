# 证据卫生：三个反复出现的失败形状

2026-08-10 一轮会话里，我（Devin）自己犯了 8 次同类错误。它们不是 8 次独立的
粗心，是**三个形状各出现了 2-3 次**。写下来是因为：这一轮已经证明「记住」不管用
——同一个形状我在意识到它之后仍然又犯了一次。

---

## 形状一：计数不是证据

### 症状

拿一个数字代替一次能证伪的实验。

### 三个实例

| 说法 | 为什么不成立 |
|---|---|
| 「零行为变更，3943 passed 佐证」 | 全绿只说明「没有测试钉住我改的地方」，不说明行为没变。该提交实际放宽了一处拒收条件 |
| 「71 failed 散在 11 个文件，我��改 1 个，故非我引入」 | 推理无懈可击，但 71 是**用错解释器**的产物，正确值 14 |
| 「失败数没变，所以没引入回归」 | 修好 3 条 + 引入 3 条 = 总数不变 |

第二条最危险：它不产生错误，它产生**看起来合理的错误结论**。前者会被立刻发现，
后者可以静默存在很久，并沿途污染所有依赖它的判断。

### 处方

**一律按名字比，不按个数比。**

- 失败归属：比测试 ID 集合，输出 新增/消失/共有，只有「新增」是本轮责任
- 读数收据：存 `failed_ids` 而非 `counts`
- 门禁基线：比「文件 + 具体字面量」，不比每文件的处数

**「行为没变」只能由实验证伪，不能由全绿推出。** 可行做法：把本次的新测试拷到
未改动的基线树上跑，因**断言**变红即证明同一输入两棵树行为不同。注意区分
ImportError（只说明新增了 API，不构成行为证据）与断言级差异。

**凡引用测试计数当证据，必须同时写明解释器路径。** 同一棵树同一时刻，宿主
python3 得 71 failed、项目 venv 得 14 failed。不写解释器的计数不可复核。


### 补充：审计计数要声明单位并闭合分母（2026-09-13）

更新按行生效、循环按去重实体计数时，`updated` 可能只是实体数，不是改动行数。一次 L2 修复审查中，真实数据全部对账通过，但收据 `updated + null` 比目标行数少了 339；差额恰好是同一股票跨榜单重复的行。**数据正确与收据可对账是两个独立断言。** 分开记录 `target_rows / matched_rows / null_rows / distinct_entities / changed_rows`，验证 `matched_rows + null_rows = target_rows`；明细可以在界面截断，审计原件必须完整或指向完整工件。同理，零目标的空跑不得仅凭 exit 0 标记修复 complete；至少验路径真实存在与目标集合非空。

证据：[L2 工具审查](/Users/a77/.finance-runtime/reviews/l2-pct-chg-54248fa3/tree/docs/handoffs/2026-09-13-l2-pct-chg-54248fa3-qc.md)。修复门禁由实现方补，本轮留了显式复现断言；没有把特定表名的脚本包装成通用工具。

### 补充：别让错误解析器定义验收分母（2026-09-19）

双索引迁移exit0，独立源集合却查出四篇非空原文零入库：页首水平线被当YAML页头，非法或非mapping也丢正文。若验收再次调用同一parser并剔除零块页，生产者和验证者会共享盲区。**应选源集合 = 实际入库集合 + 有理由的隔离集合**；不能让解析失败自己退出分母。修parser时保留原文并升切块版本，旧源未改不代表旧派生物仍有效。四篇原文SHA不动、从零恢复24/21/20/23块；14页冲突留在隔离分母，fresh不洗掉degraded。

检索探针正例也须先证明资格：L3标签不越过review_required；负例须按真实分词核posting，无完整“液冷”仍可能匹配“液”。过滤回执、词法候选、相关性、答案质量分开签；错误正负例的失败窗口原样保留，不改运行时排序/过滤凑绿。可迁移到ETL、文档解析、搜索迁移；正式解析回归与源集合对账已固化，操作脚本按冻结身份归档，未冒充长期维护器。证据：金融 `docs/handoffs/2026-09-19-kb-v4-delivery-acceptance.md`，KB23b候选未部署。

### 补充：核对真正执行和读取的对象（2026-09-12）

主测试进程的解释器相同，不能推出子进程解释器相同。一次受控复现中，只把虚拟环境 bin 前置 PATH，沙箱探针就从通过变成启动失败；它通过 PATH 选中的 venv 入口位于禁止范围，子进程 exit 71、stderr 明确为 execvp 被拒绝。这个实验支持“解释器选择足以触发失败”，不支持把缺少当时 stderr 的所有历史失败追认成同一根因，更不能替另一条间歇测试定因。

把选择过程和实际对象一并留证：父/子解释器、解析后的真实路径、参数、退出码及有界 stdout/stderr。先用环境单变量锁住失败，再通过参数化回归验证修复；不要先按“全量/单跑”的外观推断污染或负载。扫描器同理：工作目录和提交号相同也不足以说明扫描目标正确，还须核对脚本最终解析出的根目录。按同级固定仓名扫描的工具，在任意命名的 worktree 内可能读到另一棵主树；正确命名的隔离检出可在不修改检查器的情况下验证目标提交，旧误扫读数仍保留。

实现与决策：[2026-09-12 清障快照](/Users/a77/fwp-wt-instruction-gate-clearance/docs/handoffs/2026-09-12-instruction-gate-clearance.md)；原始对照：[质检报告](/Users/a77/.finance-runtime/reviews/gate-matrix-b2d40776-qc-ma8n0z52/report.md)。回归已进入现有测试；该案例不另造通用工具。

### 补充：共享 latest 不是本轮收据（2026-09-21）

并发测试结束后读 `latest.json`，可能读到别人的结果；自定义目录只有读方接入、写方仍写默认家，也会让成功测试与收据读取脱节。将唯一收据路径在运行前分配并传给写方，独占创建不可覆盖文件；共享 latest 只作导航。读回再核 revision、解释器、树、实际退出码及非零执行数，失败收据不能因“读成功”而返回 0。显式基线红集比较仍不是可带红合入的授权。

实测用真实 pytest hook 写收据后再由另一个插件替换 latest，新门禁仍读到自己的结果；另测禁用本轮收据且遗留旧 latest 时拒绝。原版首轮 21F 含两条新 helper 缺席，不把 API 不存在记成语义反例。实现：金融候选 `d5d807f80`，`conftest.py` / `scripts/run_main_gate.sh` / `scripts/main_gate_receipt.py` / `tests/test_main_gate_receipt.py`，[#814](http://127.0.0.1:3300/a77/finance-workspace-private/pulls/814)。通用设计回写 harness-reference `docs/receipt-identity-board-0921`，未合主干。

第一份完整组合又暴露继承环境的子进程会抢占父路径：`pytest --collect-only` 先落零计数，真正全量12059P结束时被不可覆盖规则挡住，门禁正确保持红。修复把owner进程ID认领前置到pytest configure，子进程不得写父收据，新顶层门禁清外层owner后重新认领。真实子进程反例旧版2F、修后相关49P；另用实际触发的收集测试经过同一门禁1P/1S且读回成功。第一轮原JSON不补写计数，新候选另跑，不能把测试stdout的通过偷换成门禁通过。

### 补充：进程身份不等于调用身份（2026-09-21）

PID（进程号）能分父子进程，分不清同一进程里的重入调用。固定金融候选 `47530e20` 的独立K3探针在外层pytest里再调用pytest.main，内层先占外层唯一收据；外层1P告警写失败，门禁却读内层2P/不同target返回0。操作员另建精确源码/环境契约的最小仓复现，子进程对照正常。**唯一文件名和不可覆盖只保护文件，不证明写者是这次调用；所有权应绑定调用/config生命周期，并验证嵌套与顺序调用。** 单补target比较也未必挡住同目标重入。可迁移到同进程任务执行器、插件重入与回调产物；未证明失败外层被放绿，不追认历史数字污染。

审查轮只审不修，原始反例见金融 `docs/handoffs/2026-09-21-ownership-k3-review.md` 与对应归档 `operator-qc/inprocess-reproduction.json`。用户随后授权修复：#814 `a092a021c` 将(PID,路径)认领凭据放入Config私有stash，并用add_cleanup在正常结束/配置失败后释放自己认领的环境状态；继承owner不清，顺序调用可重领。最终15例对精确旧hook为11F/4P、修后15P，撤Config证明/撤cleanup/同PID重领三变异均被抓住；永久守卫已进正式pytest回归，有限装置仅作证据。方法回写独占harness分支BUILD §5/KIT `9f1c80b`（未碰共享脏主树）；作者源码全量绿不等于最新main集成或独立复审。修复快照 `docs/handoffs/2026-09-21-ownership-reentrant-repair.md`。

### 补充：只读模式不豁免身份约束（2026-09-21）

同一收据工具的执行入口检查工作树，只读 `--receipt` 入口却因没有新 pytest 退出码而绕过树检查；错树、缺失、空值与错类型都被放行。**身份约束是各入口的不变量，进程退出码是仅执行模式需要的附加条件，不能用后者决定是否检查前者。** 适用于缓存读取、恢复、重放和已有工件验收。金融 `cdf6647cf` 在 #814 补了 7 个先红后绿反例（含 baseline / allow-dirty 组合），相关 56 项绿；旧原件不改、新组合另验。探针已转正式 `tests/test_main_gate_receipt.py`，无新通用工具；展开见金融协调树 `docs/handoffs/2026-09-21-ownership-resume.md`。

### 补充：审查运输成功、模型声明与有效验收是三件事（2026-09-21）

旧独立审查CLI退出0却一直取凭证失败，没有报告；新版解决鉴权后，Spec有直接探针支持，但报告分母多算一条，且源码检索带出作者摘要，不能称盲审。另一新上下文Quality在请求帽处被拒，仅一组探针完整通过，另一组被自造夹具先后阻断；没有最终质量结论。**部分断言绿不能填补未执行项，测试夹具失败也不能直接记成产品缺陷。** 原件、操作员勘误、授权预算与最终裁决分存；首尾净树还须配完整工具轨迹。

预算硬门确实挡住额外请求，不代表任务已完成；长审查还要给动态验证和报告留出预算。只收紧总帽、未保障收尾，仍会留下有日志无裁决的场。参考形状已回写 harness-reference `docs/bounded-review-0921` 的KIT/BUILD（单供应商适配，非通用SDK/OS沙箱/金额硬帽）。本例证据：金融[#815](http://127.0.0.1:3300/a77/finance-workspace-private/pulls/815)，`~/.finance-runtime/reviews/stale-closeout-k3-20260921/`；整体仍BLOCKED，不覆盖旧失败、不自动续跑。

### 补充：早建占位报告也不是收尾保证（2026-09-21）

### 补充：不限模型用量不等于资源隔离或恢复授权（2026-09-21）

固定6eb12候选的新K3两轴实际取消请求/总时长/强制收尾帽，仍在各50次准入后异常退出1、均无报告。Spec留有磁盘写入ENOSPC，Quality空stderr、提前1.282秒中断。**同时失败不证明同因；实际用量不是预算帽；进程已结束不等于交付已完成。** 共享磁盘容量回升也不能证明本轮已修复，未盘清归属不得删别人的数据或证据。撤用量预算与允许重试、修改基础设施是不同授权字段，不能互相继承。

原模型事件和shell日志、操作员QC、资源观测与封档分别留证。无OS沙箱时，契约中的路径/进程红线并非强隔离；信号测试须绑定本次创建的子PID，宽泛pkill后缺旁伤审计不能保证无旁伤。可迁移到长任务、并发CI和多agent机器。此轮未改共享harness或实现磁盘配额；六项离线自测的完成态/日志审计器及封档校验器已留作有限证据工具，不称常驻资源守卫。来源：金融 `docs/handoffs/2026-09-21-ownership-k3-v4-interrupted.md`、归档 `operator-qc/review-qc.md`；独立结论仍BLOCKED。

### 补充：缺席的审核不能算独立，恢复不能代替因果（2026-09-21）

无模型判官路径曾合成 `passed/correlated=false`，评测只读布尔值便将“没审核”计成“独立审核”。修复让私有mode优先：未审核单列no_judge、公开相关性null、独立分母排除，并把比例一路验到JSON/Markdown落盘。**标签含义依赖产生过程；禁用、未知、失败不是“另一方同意”。** 可迁移到安全扫描、数据校验、双人审批。该代码和撤保护反证已落金融#830，不仅是提醒。

同轮部署的两题真实入口成功后，就绪检查新增超时并回滚；探针在回滚前已恢复，旧版本稍后又同样超时。**接线成功、整体服务接受、答案质量、故障因果是不同断言。** 后一次绿是新观察，不能覆盖首红；“回滚后正常”不能证明回滚治好，更不能从负载/磁盘同时变化直接定因。应用于灰度发布与偶发故障调查时，原始时序比单次终态重要。

另一次误选测试收据说明：同SHA下也可能有其他脏worktree、定向或零执行收据；身份须含目标树、范围、干净/基座与实际日志哈希。失败的shell `&&` 后块未执行，不能用手写“verified=true”补签；后续真正补跑核验另留证。新出现敏感形状的失败日志阻止入Git、只存带原件哈希的脱敏副本，不为哈希一致提交疑似凭证。案例与边界：金融 `docs/handoffs/2026-09-21-judge-mode-k3-cutover.md` / `docs/verification/2026-09-21-judge-mode-k3/`；不是稳定性或金融质量通过证明。

### 补充：查询未命中不是事件不存在，自报缺口不是收据（2026-09-21）

未查询/调用失败、成功查询未命中、已收录的明确零值，是三种不同状态。只有成功查询收据能支持“本次条件与截止时点内未命中本地记录”；它仍不能证明现实事件未发生。另一主体有更晚日期，也不能证明目标主体逐日覆盖完整。子研究的gap是待核验声明，不因被父研究汇总就升格为查询收据或事实证据。

### 症状

### 三个实例

1. 依赖清单在两个门禁里各存一份，我在 docstring 写了「两处都改才算改完」——

3. 能力图谱里早有一条：「数数别用固定行号」——上一个 agent 沿用固定行号去读
   一张表，而表的起点在更上面，于是把 12 个工具数成 10 个。

最讽刺的是第 1 条：**用提醒去同步两份清单，正是这两道门禁自己要治的病。**

### 处方

**判据从事实推导，不手维护。**

- 仓内顶层包 → 扫文件系统（有 `__init__.py` 即算），新增自动纳入
- 存量基线 → 从源码 AST 解析生成，不手抄
- 主检出树 → 问 git（`rev-parse --git-common-dir` 的父目录），不写死路径
- 穷尽性 → 用测试钉住（`set(处置表) == set(类别枚举)`），��一格就红

**必须有两份时，收敛到单一真本源**，两处共读同一个文件。若两处必须各有实现

## 形状三：一个我没见它失败过的检查，不能信

### 症状

写了门禁/测试，但从未确认它在该红的时候真的会红。

### 实例与两个方向

**只验「会拦」不够**，还要验「该放行时真放行」：

- 收据的 `dirty` 判据初版按**全树** `git status` 算。而该仓工作区长期有 47 个
  脏文件（都是每日 ingest 的正常产物），于是每份收据都 dirty、校验器**永远**
  建议重跑。**永远发红的门禁比没有门禁更糟：它训练人忽略它。**
- 门禁自己的正则也会错：初版把别人源码里的**正则字符类**
  （`r"(?:/Users/|/home/|[A-Za-z]:[\\/])"`）当成路径捕获，还把**裸前缀**
  （`assert "/Users/" not in serialized`，那是脱敏断言本身）也算进去。
  假阳性混进基线比漏报更糟——基线是「存量免检」的依据，掺了假条目等于留后门。

**报错方向反了，比报不出来更糟。** 有一次���具把「基线没有这个符号」
（ImportError）误报成「行为确有变更」——而分清这两者正是那个工具存在的唯一理由。

### 处方

每道门禁至少做四项变异，缺一不可：

| 变异 | 期望 |
|---|---|
| 当前正常状态 | 通过（否则它永远发红） |

### 补充：检查器失败不是检查通过；报告兜底要脱离失败介质（2026-09-13）

`stdout == ""` 只有在子进程成功退出后才有「没有违规」的含义。真实反例：干净 HEAD 下放一个未跟踪文件，用损坏的临时 `GIT_INDEX_FILE` 让 `git status --porcelain` exit 128、stdout 空；门禁忽略 rc，仍记录 `tree_clean=true`，完整数据对账 22 项 PASS、exit 0。**被测业务正常不能弥补前置检查器没有执行成功。** Git/扫描器/权限探针等 helper 必须先核 rc，再解释内容；异常需包含命令、rc 与有界 stderr。

### 补充：独立公式不等于独立输入，副输出也是写入通道（2026-09-14）

回填验收里，SQL 映射与 Python Decimal oracle 即使分别实现，也可能共享同一个错误前驱：源行情少了一个主表已保留的日期，LAG 自动跨日，两种公式都认可错误昨收。应先证明完整依赖键集与前驱身份，再重算数值；验收分母从授权键集出发，不能按被验结果的 source 标签 INNER JOIN，否则改坏标签反而免检。精确时间窗也必须比 `(as_of,start,end)` 集合，区间内交易日计数相等不保证起点是交易日。

安全边界同理：只检查数据库连接目标，却允许 `--report-path` 对任意已有路径 `write_text`，报告仍能截断受保护数据库。所有输出文件（报告、日志、备份、状态）都要计入副作用清单，路径隔离与不可覆盖约束应在写入前落实。

### 补充：内部相等不等于外部绑定，浅层 schema 不等于结构合法（2026-09-14）

## 给存量代码加约束：棘轮，不是一次性清理

三个形状之外的一条独立收获。

51 处硬编码路径里，一部分是**故意的脱敏夹具**（喂一个像家目录的串进去，断言
输出里不含它），一部分是真实依赖，**两者同在测试目录**。所以：

- 按目录判必错
- 按「像不像脱敏」判也不行——那是语义判断，写成正则一定既漏又误伤

**所以判据是「有没有新增」，不是「是不是合理」**：存量一律免检，新增一律拦。
门禁不必理解语义，只需认出「这是新的」。基线由脚本���源码生成。

这个形状可迁移：ESLint 的 `--max-warnings`、TypeScript 渐进式 `strict` 都是它。
**「禁止变得更糟」比「要求全部合规」可落地得多**，而且不会为了让门禁变绿去
剪断现有的安全网。

同理：**清理代码时看到测试里有硬编码、魔法数字、奇怪字符串，先问「它是不是被测
对象的一部分」。** 把脱敏夹具换成动态路径，测试会变成「检查一个不存在的东西有
没有泄漏」——永远通过、什么都没测，看起来更干净实际把安全网剪断了。

## 一条 git 卫生

`git add <具体文件名>` **不足以防「提交了别人的东西」**——还要先确认该文件
**是否已被跟踪**。未跟踪文件的 `add` 是整份新增：我只改了 4 行，却把一个 219 行

## 来源身份、执行权限与主张用途不能共用一个开关

2026-09-14，金融 E2 v5 设计复审（目标 `b41e717b`，审查 `bbaa85de`）：以下为固定样本与规则对照，不宣称未实现功能已运行失败。

- **不把引用升级成命令，不等于权限已保守。** 如果真实禁令也被误吞，随后回默认 full，仍会违规外呼。已确认无约束才可用默认；边界不明应在读取前澄清或取候选解释共同允许的权限。

### 补充：继承目标不等于继承证据（2026-09-21）

金融研究续问实测：补回原日期和 local_only 后，模型能撤回旧判断，却重新查数并替换了数据；用户要求的是“只用已取得的数据”，因此仍应拒收。第二版禁止重查后又暴露“不需要检索”被投影为“不需要研究引擎”，最终只得到兜底拒答。两版都不是行为验收通过。

- 继承主体/日期、继承权限、继承证据身份是三个独立合同；一个字段恢复不代表整条链恢复。
