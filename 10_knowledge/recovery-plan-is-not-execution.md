# 恢复计划不能提前消费执行位置

## 判据

恢复函数只提出下一步、尚未执行时，不得把该步骤写成已经完成的状态推进。
同一现场重复恢复，应保留同一待办；中断结算可以持久化，但不能替代待办执行。

## 怎么判定（可执行的问法）

问：“拿到恢复计划后立即丢弃返回对象，重新启动进程，再读磁盘，下一步还在吗？”

- 同一动作与关联 ID 仍可恢复，且无重复结算：这条边界通过。
- 变成后续步骤、待发调用消失或未解释的回复被跳过：计划提前消费了执行位置。
- 结算重复追加：去重只看意图是否存在，没有按声明/调用 ID 点查已有结算。
- 任一写入确认失败却返回正常计划：确认边界失守，不能当正常恢复。

测试还要覆盖“一批部分意图落盘，先处理落盘部分，再恢复剩余部分”；单次 restore 通过不能证明可迭代。

## 适用条件

恢复与执行分离，或返回计划与实际派发之间可能崩溃的任务队列、工作流、Agent运行时。
保留完整执行位置和关联 ID，再点查结果，通常可重算计划，不必另造一份持久化计划状态。
合成事件推进确认前缀时，不应把旧预算/证据快照前缀标成已完成新效果对账。

## 什么时候我不用它

- 计划领取与状态推进处于同一事务，并持久化了可接管的待办/租约时，位置可以推进到该待办状态。
- 纯内存一次性函数不承诺崩溃恢复时，不必引入磁盘检查点。
- 当前授权已变化、deadline已过或用户取消时，不要求返回原计划，应按新事实拒绝或闭合。
- 最容易误用：同一计划重复返回不等于可以重复执行外部写操作，更不证明 exactly-once；仍需单写者和未知效果对账。

## 单写者不是效果对账

控制入口先取得同一任务的所有权，再读取检查点，整个运行/修订/恢复操作期间保持；只给 append 加锁会留下「两个控制者先读同一旧位置、随后轮流写」的窗口。

本机 POSIX 文件锁适合长模型调用：不按时间过期、进程结束后由内核释放。否了单独使用超时 lease，因为旧调用还活着时租约到期会出现双写；需要跨机时另设计带 fencing token 的租约及下游校验，不能直接推广本机锁。

- 不删或替换锁文件：同路径的新 inode 可让两进程分别取得不同文件的锁。
- 同步规范化锁的任务 ID 与实际账本 ID；修订对象必须属于受锁保护的同一存储，且内存前缀仍与磁盘一致。
- 退出前先排空在途投递、关闭旧收件箱，再释放所有权；保留未决消息，不伪造处理/丢弃记录。投递与 spool 共用可重入锁，避免反序死锁。
- 返回计划就释放了锁，计划本身不携带执行许可；实际执行器仍须重新取得所有权并复核现场。
- 锁是合作式本机协议，不约束旧版本、原始写 API 或已发出的外部请求。拿到锁不证明旧请求未执行/未计费，也不证明只执行一次。

可迁移到后台作业、消息队列消费者和断点工作流。测试至少覆盖两进程争抢、真实驱动被杀后接管、旧修订对象、在途消息与关闭交错，并拆掉保护验证测试会失败。

## 锁的范围须覆盖实际共享状态

按任务 ID 的锁只能保护该任务的账本。如果同一运行器实例还共享 inbox、取消信号等可变状态，不同任务虽然各拿到合法任务锁，仍会覆盖彼此的现场。本例两个任务都停在模型请求前，关闭 A 却关了 B 的收件箱，A 的旧箱仍接受落账。

- 同一运行器再加非阻塞实例控制锁，覆盖 run、单步驱动和 resume 的完整生命周期；不同运行器处理不同任务仍可并行。否了全局锁，因为它会无故串行化不共享状态的任务；也未把所有实例字段重构成任务映射，避免扩大改动。
- 单步生成器的 step/close 也要互斥。正在执行时拒绝竞争方，且不得把活驱动标成 finished；等待当前 step 返回后才能关闭，close 不等于取消外部请求。
- 竞争检查放在原操作状态修改与异常清理之前。测试既查竞争方被拒，也查原控制者仍活、收件箱不变、日志未增、结束后顺序复用与不同实例并行仍可用。
- 锁取得失败、磁盘读取失败和生成器异常后都必须释放实例占用；否则补的保护会变成永久忙碌。

可迁移到复用连接会话、浏览器自动化控制器和后台工作器。金融仓 9fbcc9196 的12项回归及5项撤保护实验钉住上述边界；同一作者的隔离检出仍是作者复核，不是独立审查。
