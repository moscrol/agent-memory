## 0. 一条底线（全章最重要）

> **模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。**

书里叫**参数传递的保真性**，反模式有两种：

- **静默输入转换**：工具执行前偷偷"修正"参数。书中案例是 Cursor 把中文弯引号静默
  转成直引号——模型读文件看到弯引号、原样传回去替换，工具却说"未找到匹配"。
  模型**反复失败且无法自行诊断**。
- **静默参数注入**：在模型不知情时给命令追加参数，旧版本不支持就报错，模型怎么改都错。

**必须做转换时，要在工具描述里写明，并在返回中告知模型。**

> 🔴 **我们中招了**：中转 `x.ailzd.com` **静默忽略 `max_tokens` 与
> `max_completion_tokens`**——请求 10 实得 416，且 `finish_reason=stop`（不是
> `length`）。调用方以为设了上限，实际没有，且**没有任何信号说明**。
> 这是教科书级的静默输入转换，也是我们预算算不准的根因之一。
> 详见 `finance-workspace-private/docs/verification/2026-08-09-episode-seam-ladder-live.md` §5.4。

同族的一条推论：**静默截断同样危险**——Agent 会误以为自己看到了全部内容。
截断必须显式可见（省略了多少、怎么读剩下的）。

## 1. 能力表达形式：专用工具 还是 Skill + 通用执行器

三维决策：

| 维度 | 偏专用工具 | 偏 Skill + 通用执行器 |
|---|---|---|
| 参数复杂度 | 嵌套对象、多字段联合校验 | 参数简单，CLI 传参就够 |
| 变更频率 | 稳定的底层操作 | 频繁变化（改文本 << 改代码+测试+部署） |
| 模型能力 | 弱模型需要 schema 引导 | SOTA 模型可少工具多 Skill |

## 2. 粒度与通用性

- **整合判据**：功能相似性 + 使用场景重叠度。`extract_pdf/docx/pptx` → 合成
  `read_document(file_type=...)`。但参数形态/延迟特性差异大的**别硬合**（OCR vs 视频抽帧）。
- **通用工具优于专用工具，除非有明确的安全/权限/性能理由**。`code_interpreter`
  胜过十几个专用计算器——**利用模型的代码生成能力，而不是限制它**。
- 边界：需特殊权限、复杂配置、有安全风险的操作，仍要封装专用工具
  （例：各平台 grep 语法不同，给专门的 grep 工具更好）。
- 工具数超过约 **100 个**，最强的模型也会选错。

## 3. 工具描述的艺术（投入产出比最高的一项）

- 核心是让模型知道**"什么时候用"**，不只是"能做什么"。
  ❌「搜索相关内容」→ ✅「当需要获取实时信息或查找未知事实时使用」
- **清晰列出边界——做不到什么、不接受什么输入——往往比描述能力更重要。**
  > **大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么。**
- 参数用**具体例子**代替抽象规范：`+8613888888888` 胜过「E.164 格式」。
- 返回值也要描述；耗时工具要注明代价（"大型网站 5-10 秒，只要元信息请用 X"）。
- **每个工具附 1-5 个真实调用示例**。JSON Schema 表达不了"时间戳是秒还是毫秒"
  这类隐式约定。加示例后准确率可从约 72% → 90%（因任务而异）。
- 🔑 **调试原则：Agent 频繁选错工具时，优先检查工具描述，而不是怀疑模型能力。**
  修描述的投入产出比通常高于换更强的模型。

> ✅ **我们实测过了，而这条判据在我们这里不适用**（2026-08-09）。

## 4. 五类工具与各自的设计重点

| 类型 | 调用方向 | 作用对象 | 设计重点 |
|---|---|---|---|
| 感知 | Agent 主动 | 获取信息 | 粒度、输出量控制、分页、**显式截断**；只读 → 可缓存、可并行 |
| 执行 | Agent 主动 | 改变世界 | 分层安全、提议者-审核者、Sidecar、**幂等性** |
| 协作 | Agent 主动 | 驱动其他 Agent/人 | 生命周期原语（spawn/send/cancel/list）、HITL 超时降级 |
| 用户沟通 | Agent 主动 | 触达用户 | 异步消息、多渠道、用户召回 |
| 事件触发 | **Agent 注册、外部触发** | 唤醒 Agent | 触发条件过滤、事件载荷要够用 |

**感知工具**：搜索类返回结构化候选列表（标题/位置/摘要）而非全文拼接；读取类支持
`offset/limit`；超阈值截断要注明"已显示 1-200 行，共 5000 行，可用 offset 继续"。

**执行工具**的安全分层：输入验证（快速失败，**不尝试"智能"修正**）→ 权限控制
（黑名单只是最基础层，可被变形绕过）→ 沙盒隔离。
⚠️ **venv 不是沙盒**——它只隔离包依赖。真沙盒按强度：OS 级（Seatbelt/seccomp）
< 容器 < microVM，再叠资源配额。

**执行-验证-反馈闭环**：**结果可被验证就应自动验证**。`write_file` 后立刻跑 linter，
把结构化错误列表作为返回值的一部分交回 Agent。

**长输出**：头 50 行 + 尾 50 行 + 中间注明省略多少 + 落盘并给出读取路径。

## 5. 提议者-审核者 与 Sidecar（我们最该改的一处）

两种独立的第二视角，**时机与审查对象不同**：

| 维度 | 提议者-审核者 | Sidecar |
|---|---|---|
| 时机 | 操作前（事前审批）/ 操作后（事后验证） | 与流式输出并行，**门控单次工具调用** |
| 审查对象 | 操作的合理性 / 操作的结果 | 操作本身（工具调用） |
| 输入 | 提议者与审查者看到相似信息 | **刻意隔离主模型的自由文本** |
| 模型 | **能力相近但训练偏好不同** | 轻量模型足够（结构化分类问题） |

关键设计点：

- 🔑 **提议模型与审批模型应来自不同家族**（如 GPT 系 vs Claude 系），**能力相近**。
  > 同家族的训练数据与偏好相似，**容易在相同场景犯相同错误**。
  能力差距过大也不行（审查者跟不上被审者思路）。
- 两者的底层规则必须一致（否则互相扯皮），但**关注点应不同**：提议方重任务完成，
  审批方重风险控制。
- **审批失败不要简单重试**，而应把拒绝理由**作为工具调用结果加入轨迹**——
  从提议方视角看就是一次工具失败，Agent 本来就会处理。
- Sidecar 只看结构化字段（工具名、参数），**不看自由文本**——防止攻击者用话术
  经主模型复述来操纵权限判断。
- **拒绝熔断器**：连续多次拒绝不应无限重试，应回退到人工判断。
- 事后验证的要诀是**模态切换**——不是让第二个模型重读一遍，而是换个模态检验
  （生成文档→渲染成图看排版；改配置→沙盒里实跑）。

> 🔴 **我们的 semantic judge 违反了第一条**：`SemanticEpisodeVerifier(primary_judge=client)`
> 传的就是**写答案的同一个 client、同一个模型**，属于书中点名的**相关审查**。
> 代码里的 `llm_refine.judge_provider()`（`LLM_JUDGE_*` 独立端点）正是为解耦而设，
> **当前未配置，那条路径整个被跳过**。
> 配上独立 judge 端点会**一次解决两个问题**：① 去相关（书上的正确性理由）；
> ② judge 不再和草稿生成抢同一笔 synthesis reserve（我们实测 judge 在
> 15s/7.5s/7.5s 窗口上三次全部 `TimeoutError`）。

## 6. 事件循环与安全点（回答"截断为什么落在干净边界"）

书里给了这个问题的标准答案，与并发编程同构（Go `for { select {} }` / `ctx.Done()`）：

> **事件只在每轮循环的边界被消费。** 当 LLM 正在推理、工具正在执行时，新到达的事件
> 不会凭空插入打乱当前步骤，而是先在队列中等待，待本轮到达一个**安全点**
> （一段推理结束、一次工具返回）再统一处理。**取消也遵循同样的纪律**——
> 不在任意时刻强行掐断，而是在安全点检查是否被要求停止。

三种处理策略的差别，仅在于**对待安全点的方式**：

| 策略 | 用于 | 对安全点做什么 |
|---|---|---|
| 取消式 | 紧急（用户喊停、监督指令） | **主动提前制造**一个安全点 |
| 队列式 | 常规（工具返回、补充信息） | 等到下一个自然安全点，批量追加 |
| 并行式 | 独立轻量查询（"今天天气"） | 另起一个循环，不等主循环 |

判定建议用**轻量分类 LLM 做事件路由**，硬编码规则表达力不够。

**队列式的已知缺陷**：批量追加时**模型只关注最后一个事件**。缓解靠状态栏显式编号
（`[未处理事件 1/4] ...`）+ 末尾汇总。

> 🟢 **这条我们已有等价实现**：`agent_episode.py` 在轮次边界求值预算，
> `_opening_planning_timeout` 处理首轮借用。竞品 knevo 的"截断天然落在 turn 之间"
> 也是同一机制。**不必重新发明，但要对照检查取消是否也走安全点**（我们的 batch 场景
> 无取消源，暂不适用）。

## 7. 工具规模化：MCP / 动态发现 / Skills

- **MCP** 解决**互操作**（一次开发处处可用）；**Skills** 解决**选择过载**，
  把"工具选择"问题转化为"知识检索"问题。
- MCP 上下文开销真实存在：5 个 server 可达约 55K token。Cursor 的缓解方案
  （工具描述同步到文件夹、默认只给名字索引）A/B 实测**总 token 降 46.9%**。
- **动态工具发现**：Anthropic 实验中 Opus 4 工具使用准确率 **49% → 74%**；
  MCP-Zero 在约 2800 工具上省约 **98% token**。
- **KV Cache 代价**：动态加载会破坏静态前缀。正解是把变动部分**追加到上下文末尾**，
  且**只在被发现的那一轮追加**，此后固定在原位成为普通历史（不是每轮搬到末尾）。
- **Skills 的渐进式披露**：启动只看 `name` + `description` 目录（数百 token），
  真正需要时才往下读——**像查工具书，不是从第一页读到最后一页**。
  好处是不必维护向量索引，靠通用文件阅读能力即可。

**MCP 安全四类风险**：工具描述投毒（description 原样进上下文，是提示注入变种）、
恶意/被劫持服务器（供应链）、**同名工具遮蔽**、凭证管理。
缓解：接入前**把 description 当不可信输入审计**、锁版本拒绝静默更新、每个 server
配最小权限凭证。

## 8. 幂等性与取消语义（执行工具专属）

> **一次调用被取消或超时时，它的副作用到底发生了没有？**

- **幂等**手段：唯一标识（idempotency key）服务端去重；或**先查询后变更**。
- **不可幂等**的操作（发邮件、打电话、转账）用**"预检-确认"两段式**：
  第一段只校验预演并返回确认令牌，第二段凭令牌执行；执行阶段失败**不就地盲目重发**，
  交回上层重走预检。

## 9. 工具设计的三代演进

1. **第一代**：直接 API 封装，一端点一工具，粒度过细。
2. **第二代 ACI**（Agent-Computer Interface，对标 HCI）：工具应对应
   **Agent 的目标**而非底层 API 操作。粒度/通用性/描述规范都属这一代。
3. **第三代**：优化调用（示例驱动）、发现（动态发现）、**串联（代码编排执行）**。
   代码编排：模型一次生成脚本，中间变量留在执行环境，只返回最终结果，
   **token 消耗可降约两个数量级**。

### §3 那条判据这次**成立了**，且拿到了干净对照

上一版记的是「12 工具仅 6 个有契约」与「17% 出错率不是描述造成的」。前者已过期
（现为 12/12），后者仍成立但**不能推广**——那次是超时，这次是真的描述问题。

`finance_query` 的参数描述改前 / 改后（同题集、同模型 gpt-5.6-terra、同为
`--repeat 3`，改前臂在临时 worktree 跑）：

| | 改前 | 改后 |
|---|---|---|
| 合法率 | **55.9%** | **87.9%** |
| 靠 harness 代偿才合法 | 16 | 2 |
| `order_by` 写成单对象而非数组 | **14** | **0** |

关键在于：`order_by` 的 schema **本来就写着 `"type": "array"`**。
**光有类型挡不住，缺的是例子**——这正是 ch4 §3「JSON Schema 描述得了类型，
描述不了典型的参数组合」那句话的现场，也是族 A 官方 custom-tools 用
`.describe("… e.g. kilometers, fahrenheit")` 示范的同一件事。**A×C 跨族一致。**

### 三条比结论更耐用的方法教训

1. **N=1 的读数两头都会骗你，且方向相反。** 同一个实验里：改前 N=1 报 30.8%
   （悲观，真值 55.9%），改后 N=1 报 100%（乐观，真值 87.9%）。
2. **噪声带要用干净配对量，不能估。** 两次**首轮条件完全相同**的 `--repeat 3`
   跑出 87.9% 与 100% → **噪声 ≥±12pp（n≈30）**。所以 55.9%→87.9% 这个
   32pp 的效果是真的，但**精度远没有数字看上去那么高**。
3. **文档化单条约束的边际收益递减。** AST 扫出 `FinanceQueryValidationError`
   共 **35 处**，其中一大批是 schema 结构上表达不了的**跨字段约束**
   （`group_by` 必须等于 `dimensions` 全集、排序字段必须已被选中……）。
   每补一批描述，被点名的那几条归零，长尾就换几条新的顶上来。
   **逐条写描述是打地鼠，35 条的长尾要靠结构性做法。**

### 测不到的那一条：拒绝理由回灌

族 A 幸存蒸馏稿把「工具被拒时作为 tool result 回灌」标为**最该抄的一条**，
本轮发现我们**根本没做**：模型收到的逐字是
`{"ok": false, "error": "invalid_arguments", "detail": ""}`——
`detail` 字段早在结构里，从没被填过；原因在 `registry.prepare()` 被丢弃。
这解释了基线的形状：**15 次失败里 14 次是同一个错误一模一样地重复**。

已修（`0c1b1b46`，对全部 12 个工具生效）并建了多轮探针（`9f6ca142`），
但**自愈率仍是 null**：描述修好之后失败已经稀少，最近一次 `--repeat 3`
跑出 30/30 全合法，**没有可修的东西，回灌路径压根没触发**。

> 🔑 **可迁移**：一个「防御性修复」的效果，在缺陷率已经降下来之后就测不出来了。
> 这不代表它没用（长尾还在），但**要测就得趁缺陷还多的时候测**，
> 或者刻意构造失败样本。顺序错了就永远补不回来。

### 量具本身的四次自我证伪（每一次都改了结论）

建 `scripts/probe_tool_arguments.py` 时踩的，全部留了注释：

1. 保真性观测嵌在 `valid` 分支里 → 字段错误先抛就跳过，**一个错法掩盖另一个的计数**
2. 汇总函数把同一个毛病又犯一遍（取值处修了，聚合处没修）
3. provider 报错的样本被记成「模型没调工具」→ 首跑 8/8 全是 `未配置 LLM key`、
   0.0 秒、配额没花，**却给出一份看着干净的 summary**。已改 fail closed + 退出码 2
4. 模型调用花完、读数算完，**最后一步落盘崩在 `mappingproxy` 不可序列化**
   （`dict()` 只转最外层），8 次配额白花。dry-run 的 stub 参数太浅覆盖不到嵌套路径

### 但对表之后，真正的结论是：四处超时是同一个问题

把当天实测的四个数摆在一起，它们全部是**同一条递减 deadline 的切片**：

| 组件 | 分到的上限 | 实测需要 |
|---|---|---|
| 首轮模型调用 | 69.77s | 草稿 26–91s（另有一次 135s） |
| 工具批次（`news_search`/`evidence_search`） | 30s | **超时** |
| judge 三次尝试 | 15 / 7.5 / 7.5s | **>15s** |
| synthesis reserve 总额 | 60s | 草稿与 judge **共用** |

**这套时间标定对应的是一个比我们当前 provider 更快的模型。** 不是四个 bug，
是一次标定与一次换模型之间的落差。

**下一步优先级**（2026-08-09 修订，前一版第 2 条已被实测推翻）：
1. **重新标定这条 deadline 的各段**，依据是实测速率（terra ≈45–52 tok/s、
   sol ≈34–43 tok/s），不是拍脑袋改常数。改之前先想清楚：抬一段就是从另一段拿，
   已实测过抬 judge 窗口会把草稿饿死。
2. 配 `LLM_JUDGE_*` 独立端点——**只解决去相关**（书中的正确性理由）。
   ⚠️ 更正：它**不会**给 judge 独立预算——`attempt_timeouts` 在
   `episode_semantic_verifier.py:1092` 只算一次，两条 judge 路径共用同一个
   deadline。只有换成更快的 judge 模型才顺带缓解超时。
3. 让草稿更短——**收窄输出结构**，不是写"请简短"（中转不认 `max_tokens`）。
