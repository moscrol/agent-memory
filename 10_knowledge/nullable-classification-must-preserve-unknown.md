# 可空分类不能把未知压成否定

## 失败形状

SQL 有真、假、未知三种逻辑值。查询结果里的 NULL 到 Python 常成为 `None`；直接 `bool(None)` 会丢失“未知”的含义。若后续算法将 False 当作确定的停止条件，就可能产出形式完整但依据不足的事实。

2026-09-24 行情恢复发现：当天名称有效、前一天名称为空时，前一天涨停判断的 SQL NULL 被转成 False，连续涨停高度从 2 静默变成 1；同一行空字符串又能得到 2。正确做法不是猜两板，而是拒绝没有足够身份依据的连板结论。

## 处理原则

1. 在数据边界保留未知，别用 `bool(...)`、`or False`、`COALESCE(..., false)` 将它默认为否定。
2. 在实际消费未知时拒绝，而且要在删除旧结果、写入新结果之前拒绝。
3. 按依赖范围校验。连续窗口已经被一条有效的非涨停行截断，就不必再校验更早的名称；只计算当天总览，也不必承受未消费的历史连板缺口。
4. 可选指标的宽泛异常降级不能吞掉必需身份错误。需要单独的错误类型，并在通用 fallback 前重新抛出。
5. 错误应带实体身份与真正缺失的日期，而不是只报当前目标日。

不要把“按需校验”解释成忽略未知，也不要把严格校验解释成全表任一旧缺口都阻断所有功能。边界取决于本次计算实际依赖哪些行。

## 验证

必须同时有拒绝与放行控制：消费无效历史名时失败且旧派生表逐列不变；当天非涨停、有效断板后的更早缺名、无需连板的当日总览仍可计算。反例应在旧代码上失败，再对精确修复版本执行。

## 限定

本次 `bool | None` 中的 None 专指无效名称造成的未知，不能未经调整就拿它表示价格、参考价、交易状态等其他缺口，否则错误类型会误报。多个原因需要共存时，考虑携带原因的显式未知类型。

非空名称不证明名称属于目标日期；通过单条计算保护，也不证明全市场身份全集、复权完备性或发布编排通过。代码门与数据证据门必须分别验收。
