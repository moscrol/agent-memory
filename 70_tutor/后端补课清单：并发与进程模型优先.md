# 后端补课清单：并发与进程模型优先

> 结论：六张地图全是**静态结构**（实现在哪 / 能力节点 / 入口 / 骨架六层 / 闭环原理 / 数据落哪），

## 一句话先懂

- 锁只在它的「互斥范围」内有效：进程内锁管不到第二个进程，文件锁管不到第二台机器。
  你的仓库里三个层级各有一处实现，是现成教材。
- 「阻塞」不是慢，是**占着一个别人也要用的位置不放**（线程、连接、写锁）。

## 为什么先补这块，不是别的

1. 简历上「配额在副作用前预占并原子取号」一句，面试官下一问必是「uvicorn 开 4 个 worker 会怎样」。
   答案在 `intelligence/api/quota.py:13-16` 的边界声明里，但要能用自己的话讲出**为什么**。
2. 内测多用户先炸的是并发（2 个 run worker、SSE 每连接占一线程），不是召回率。
3. 数据库事务、任务队列、韧性模式全部建立在「原子性 / 互斥范围 / 阻塞」这三个概念之上，跳过它们后面是背表。

## 仓库实物教材（先读这些，再读书）

### 三级锁

| 层级 | 位置 | 互斥范围 | 出了范围会怎样 |
|---|---|---|---|
| 进程内锁 `threading.Lock` | `intelligence/api/quota.py:50,79` | 同一进程的所有线程 | 多 worker 时每进程一把锁，配额放大 N 倍 |
| 同机跨进程锁 `fcntl.flock` | `scripts/claim_ledger_id.py:118-147` | 同一台机器全部进程（内核仲裁） | 跨机器无效；NFS 上不可靠 |
| 存储层锁（DuckDB 单写者文件锁） | `market_feature_store/db.py:10-12,200-215` | 同一个 .duckdb 文件 | 长事务持写锁 14 分钟饿死所有只读连接（实测过，处方 = staging 副本 + `os.replace`） |

### 两个阻塞点

- SSE 事件流 `intelligence/api/app.py:2693-2741`：同步生成器 + `time.sleep(0.5)` 轮询，
  Starlette 把同步迭代派到线程池执行，**每个挂着的 SSE 连接占一个线程池线程**（anyio 默认 40）。
  自用没事；40 个人同时开着页面，其他同步接口排队。
- run 执行器 `RunSupervisor` `intelligence/api/app.py:511,1017-1110`：`_WORKER_COUNT = 2`，
  无准入控制，第 3 个并发 run 进 `ThreadPoolExecutor` 队列静默等待，
  而 15 分钟总期限（`CancellationSignal.deadline_expires_at`）与 `threading.Timer` 在 `_submit` 时就开始计时。

### 一个生命周期陷阱（已修对，要能讲原理）

- `intelligence/api/auth.py:357-362`：纯 ASGI 中间件 vs `BaseHTTPMiddleware`。
  响应头发出与响应体流完是两个时刻；只包住前者的中间件管不到流式响应的 body。

### 已做对、只差命名的模式

- deadline 全链传**绝对时刻**（`CancellationSignal.remaining()` `app.py:1011-1014`）：
  术语 deadline propagation（gRPC 同款）。相对超时每跳一层重新计时，误差累积；绝对时刻各层各算剩余。
- staging 副本写完 `os.replace` 换名（`db.py`）、读 VIEW / 写 generation 表 / 快照 id 进主键：
  术语「不可变数据 + 原子切换指针」，与蓝绿发布同构。
- FOMO FLOW 渠道健康度状态机：术语 circuit breaker 三态 closed / open / half-open；
  按成本 / 延迟 / 健康度择优 = 负载均衡策略；亲和恢复 = 会话粘性（session affinity）。

## 术语对照

- `GIL`（全局解释器锁）：CPython 内同一时刻只允许一个线程执行字节码；I/O 等待时会释放。
- `事件循环`（event loop）：单线程内轮流处理就绪 I/O 事件的调度器；一个同步慢调用会卡住全部协程。
- `check-then-act`：先读状态再据此写入，两步之间可能被插队；解法是把两步放进同一个临界区或用原子操作。
- `幂等`（idempotent）：重复执行与执行一次结果相同；是「失败就重试」安全的前提。
- `MVCC`（多版本并发控制）：写入生成新版本而不覆盖旧版本，读者看快照，读写互不阻塞。
- `WAL`（预写日志）：先顺序写日志再改数据页，崩溃后靠日志恢复。
- `SSE`（Server-Sent Events）：服务端单向推送的 HTTP 长连接，浏览器原生支持自动重连。
- `ASGI`：Python 异步 Web 服务器与应用之间的接口协议（同步版叫 WSGI）。
- `deadline propagation`：把绝对截止时刻沿调用链传下去，每层自算剩余预算。
- `circuit breaker`（熔断器）：连续失败后进入 open 拒绝调用，一段时间后 half-open 放一发探测，成功则 closed。

## 自测题

- 为什么 `threading.Lock` 出了进程就失效？`fcntl.flock` 为什么出了机器就失效？
- `RunSupervisor` 只有 2 个 worker，第 3 个请求进来会发生什么？它的 15 分钟从哪一刻开始算？
- SSE 端点从 `def` 改成 `async def` 后，线程池的压力去哪了？还剩什么压力？
- 你的 VIEW / generation / snapshot_id 模式相当于 MVCC 的哪一半？缺的那一半是什么？
- deadline 为什么传绝对时刻不传相对秒数？

<details>
<summary>参考答案</summary>

- 进程内锁是进程私有内存里的一个标志位，第二个进程有自己的一份；`flock` 由本机内核仲裁，另一台机器的内核不知道它。
- 静默进 `ThreadPoolExecutor` 队列等待；`CancellationSignal` 的截止时刻与 `threading.Timer` 都在 `_submit` 时创建，排队时间会吃掉执行预算。
- 轮询的 sleep 不再占线程；但 `store.load_stream_events` 仍是同步文件读，要么 `to_thread`，要么改成事件通知。
- 相当于「写新版本不覆盖旧版本 + 读者看已发布快照」；缺的是数据库层自动的版本可见性判定与垃圾回收，靠人工台账（candidate / published / superseded）代替。
- 相对秒数每经过一层就重新计时，等待与排队时间不被扣除，误差跨层累积；绝对时刻各层用「截止 − 现在」自算剩余，天然扣除了所有等待。

</details>

## 跨领域同构

- 任何「计数器 / 发号器 / 限流」需求，第一个问题永远是「互斥范围要覆盖到哪一级」。
- 「不可变数据 + 原子切换指针」= 蓝绿发布 = Git 的 ref 更新 = DuckDB staging 换名。
- 「阻塞占位」的分析方法（谁占了什么、多久、别人等不等）适用于线程池、连接池、数据库锁、LLM 并发配额。
