# 好工具如何被定义：通用评估骨架与类型专属断言

## 一句话先懂

好工具不是“调用成功率高”，而是在明确的业务目标和安全硬约束下，满足可观察的工具契约，并通过通用质量骨架、工具类型专属断言和端到端任务评估。评估不是寻找一个万能分数，而是把“好”拆成可以验证、比较和反驳的条件。

## 大白话解释

把工具想成公司的一个岗位。不能因为员工“成功接到电话”就说他工作完成了：

- 电话接通了，但找错了客户；
- 客户找对了，但传错了合同；
- 合同传对了，但重复发送了两次；
- 全部流程看似成功，却把“可能受益”说成了“确定受益”。

同样，Agent 工具返回 HTTP 200 或执行函数不报错，只能说明“请求被接受并执行了”。真正要问的是：

```text
有没有完成业务目标？
返回的数据是否语义正确？
有没有违反安全约束？
失败时是否可诊断、可恢复？
```

“好”不是设计者凭感觉说“我觉得清楚”，而是把目标写成契约，再用样本、断言、人工抽样和生产反馈不断检验。

## 第一性原理推导

1. **工具调用是一条链路，不是一个点**：用户问题 → LLM 理解 → 工具选择 → 参数生成 → Harness 传递 → 工具执行 → 返回包装 → Agent 解释。
2. **任何一环出错都可能造成最终失败**：工具执行成功，不代表参数正确；参数正确，不代表查询对象正确；数据正确，不代表最终解释没有越界。
3. **业务目标比协议状态更高一层**：HTTP 200、JSON 合法、函数返回，不等于用户目标完成。
4. **不同工具的“正确对象”不同**：感知工具主要验证事实和来源，执行工具主要验证副作用和状态，沟通工具主要验证收件人、内容、时机和频率。
5. **安全事故不能被平均分数抵消**：一次越权写入或敏感信息泄漏，不能用其他任务的高成功率冲销。
6. **人无法预见所有边界**：因此必须用评估集、对抗样本、生产轨迹和人工校准，把未知问题逐渐变成可回归的测试。

因此推出：

```text
业务目标 + 安全约束
→ 工具契约 / Gold 标准
→ 正常、边界、对抗评估集
→ 自动断言
→ 人工抽样与评审器校准
→ 灰度运行与失败轨迹
→ 把新失败固化为回归样本
```

## 技术映射

### 一、先定位错误第一次出现在哪里

以用户说“查昨天算力 PCB 的成交额”为例，返回了错误日期。不能直接认定工具实现有错，要逐层定位：

| 现象 | 可能责任层 |
|---|---|
| Agent 把“昨天”解析成错误日期 | 意图解析、上下文或工具描述 |
| Agent 传对了，Harness 改错了 | 参数传递层 |
| 工具收到正确日期，却查了错误分区或错误表 | 工具实现 |
| 工具查对了，却把返回日期包装错 | 返回适配层 |
| 工具和返回都对，最终答案写错 | Agent 结果解释层 |

### 二、通用评估骨架

所有工具都可以先检查六个维度：

| 维度 | 核心问题 |
|---|---|
| 契约正确性 | 输入、输出、空结果、失败语义和副作用是否清晰？ |
| 功能正确性 | 工具是否真的完成它声称的功能？ |
| 异常鲁棒性 | 缺参、空数据、超时、重复、并发和中断时是否可控？ |
| 安全性 | 是否越权、泄漏、静默改参或绕过审批？ |
| 运行质量 | 延迟、超时率、重试次数、成本和可观测性如何？ |
| Agent 可用性 | Agent 是否选对工具、传对参数、知道边界并能恢复？ |

其中安全性通常是硬门槛：

```text
越权访问 = 0
未授权写入 = 0
敏感信息泄漏 = 0
静默参数改写 = 0
```

### 三、通用骨架 + 类型专属断言

| 工具类型 | 专属正确性断言 |
|---|---|
| 感知工具 | 返回数据、日期、对象、来源和时点正确；空结果可解释 |
| 执行工具 | 外部状态改变正确；重复调用幂等；范围、审批、回滚和审计正确 |
| 协作工具 | 任务边界、上下文、权限、终止条件和结果验收完整 |
| 用户沟通工具 | 收件人、内容、时机、频率和不确定性表达正确 |
| 事件触发工具 | 不漏触发、不重复触发；失败可重试；重启可恢复；状态可追踪 |

这不是“每类工具都重新发明一套标准”，而是：

```text
统一质量骨架
+ 工具类型特有的正确性断言
+ 业务场景的具体验收条件
```

### 四、工具实现、Agent 使用和端到端任务要分开

| 层次 | 测试方式 | 主要检查 |
|---|---|---|
| 工具实现 | 给工具正确参数直接调用 | 查询/写入/发送本身是否正确 |
| Agent 使用 | 给 Agent 用户问题 | 工具选择、参数语义、重试和边界理解 |
| 端到端任务 | 从用户目标完整运行 | 正确的人、正确的数据、正确时机、正确次数和证据边界 |

可用下面的关系理解：

```text
最终任务质量
= 工具实现质量
× 工具描述质量
× Agent 选择能力
× Harness 恢复能力
```

### 五、自动评估、人机协同与人工校准

#### 1. 确定性规则：优先自动化

```python
assert returned_date == requested_date
assert result["status"] in {"ok", "no_data", "error"}
assert read_only_tool_did_not_write_database
assert duplicate_write_count == 1
```

适合自动检查日期、代码、字段、数值范围、权限、副作用、重复调用、Schema 和延迟。

#### 2. 不变量与变形测试

不变量（invariant）是无论输入怎么变化都必须成立的性质：

```text
请求日期是什么，source_date 就必须是什么
同一写入请求调用两次，记录数不能增加两条
只读工具调用前后，数据库状态必须完全一致
```

变形测试（metamorphic testing）是在不知道每个输入精确答案时，测试输入变化后结果是否遵守关系：

```text
日期从 07-30 改成 07-31 → source_date 也必须改变
同一写入请求重复一次 → 记录总数不能增加
排序方向改变 → 记录集合不变，只改变顺序
```

#### 3. Gold Set：有标准答案时自动比对

```json
{
  "question": "查询 2026-07-31 算力PCB",
  "expected_tool": "query_sector_daily",
  "expected_date": "2026-07-31",
  "expected_sector": "算力PCB",
  "expected_fields": ["pct_chg", "amount", "diff_ratio"]
}
```

可以自动检查工具选择、日期、板块、字段和数值是否符合标准。

#### 4. 语义质量：LLM Judge 加人工抽样

LLM Judge（模型评审器）不应只回答“好不好”，而应按 Rubric（评分规约）逐项判断：

```text
1. 是否给出数据日期？
2. 是否区分事实和推断？
3. 是否说明来源？
4. 是否暴露数据缺口？
5. 是否给出无依据的确定性结论？
```

评审结果应带证据：

```json
{
  "criterion": "是否区分事实和推断",
  "pass": false,
  "evidence": "使用“确定受益”，但没有给出预测依据"
}
```

人工重点审核高风险、新类型、自动评估失败、评审器不确定和自动结果与用户反馈冲突的样本，而不是逐条检查所有正常调用。

### 六、以 `send_research_alert` 为例

工具调用成功率 99%，但实际出现：发错研究员、重复发送、把“可能受益”改成“确定受益”。对应的评估是：

```text
发错人
→ recipient ∈ whitelist
→ actual_recipient == expected_recipient

重复发送
→ 唯一键 event_id + recipient_id + alert_type
→ 同一请求调用两次，发送记录数仍为 1

内容被改写
→ 确定性规则检查禁止措辞和必需限定词
→ 语义评审检查是否把推断升级为事实
→ 高风险样本人工抽查
```

“发送成功率”只能说明工具请求完成，主要属于工具执行/运行质量指标；它不等于 Agent 选对工具，也不等于端到端任务成功。

## 术语对照

- `Tool Contract`（工具契约）：输入、输出、错误、边界、副作用和权限组成的可验收约定。
- `Gold Set`（标准样本集）：每个样本带有期望工具、参数、字段或答案的评估数据集。
- `Rubric`（评分规约）：把“好不好”拆成可逐项判断的评分标准。
- `LLM Judge`（模型评审器）：按预设标准评估另一段模型输出的模型；不能默认等同于人工真值。
- `Invariant`（不变量）：无论输入如何变化都必须保持成立的性质。
- `Metamorphic Testing`（变形测试）：通过改变输入并检查输出关系来测试系统，即使没有每个输入的精确标准答案。
- `Regression Test`（回归测试）：把已发现的失败固化成样本，确保后续修改不会重新引入。
- `Gated Evaluation`（门控评估）：先检查不可突破的安全/权限硬约束，再比较成功率、延迟和成本等软指标。
- `p95`（95 分位延迟）：100 次请求中，最慢的 5 次之外的最大耗时，用于观察长尾体验。

## 本轮场景对照

当前金融 Agent 中，查询行情、写候选池、推送研究提醒的评估对象不同：

```text
查询行情
→ 日期、板块、字段、数值、来源、空结果语义

写候选池
→ 数据状态、幂等、权限、审计和回滚边界

推送研究提醒
→ 收件人白名单、发送次数、���实/推断边界和发送时机
```

如果工具调用成功率高但日期经常传错，不能只看 HTTP 成功；应把错误加入评估集，并先定位是工具实现、工具描述、参数解析、Harness 传递还是结果解释的问题。

这在 RAG、数据管道、推荐系统和量化回测中同样适用：先写可验证契约，再设计样本和指标，不把单一平均分当真相。

## 边界与反例

- **反例：HTTP 200 就算成功。** 协议成功不等于业务语义正确。
- **反例：所有工具用一个总分。** 不同工具的正确性对象不同，必须保留类型专属断言。
- **反例：只看调用成功率。** 工具可能接受了错误日期、错误对象或错误权限请求。
- **反例：安全违规可以被高成功率抵消。** 越权、泄漏、未授权副作用通常应是硬门槛。
- **反例：LLM 自审可以独立作为门禁。** 生成者和评审者完全相同，容易形成“自己写错、自己判定通过”的闭环。
- **边界：人工不是所有语义判断的唯一方法。** 能形式化的规则应自动化；人工重点放在复杂、新颖、高风险和冲突样本。
- **边界：Gold Set 也不是永远正确。** 标准答案可能过期或口径错误，需要来源、时点和人工复核。

## 可复用检查清单

- [ ] 是否先定义业务目标，而不是把 HTTP 200 当成功？
- [ ] 是否把工具链拆开，定位错误第一次出现的责任层？
- [ ] 是否同时定义通用质量骨架和工具类型专属断言？
- [ ] 是否把工具实现、Agent 使用和端到端任务分开评估？
- [ ] 是否为日期、代码、字段、数值、权限和副作用建立自动断言？
- [ ] 是否用不变量或变形测试覆盖设计者未想到的输入变化？
- [ ] 是否把已发现失败固化为回归样本？
- [ ] 是否对 LLM Judge 使用结构化 Rubric 和证据，而不是只看总分？
- [ ] 是否把安全违规设为硬门槛，而不是普通扣分项？
- [ ] 是否保留人工抽样来发现新型长尾并校准自动评估？

## 自测题

1. 一个 `send_research_alert` 工具调用成功率 99%，但有时发错研究员、有时重复发送、有时把“可能受益”改成“确定受益”。请分别说明哪些可以自动评估，哪些需要人工或 LLM Judge 辅助，以及发送成功率应放在哪一层。

<details>
<summary>参考答案</summary>

发错研究员可以用白名单和 `actual_recipient == expected_recipient` 自动断言；重复发送可以用唯一键和重复调用测试自动验证；内容是否把推断升级为事实，可以先用禁止措辞/必需限定词规则，再用结构化 LLM Judge 和人工抽样校准。发送成功率主要是工具执行/运行质量指标，不等于 Agent 工具选择成功率，更不等于端到端任务成功率。

</details>

2. 你发现工具返回了错误交易日，应该立刻修改工具实现吗？

<details>
<summary>参考答案</summary>

不应直接跳到结论。先用带有正确参数的直接工具测试定位：Agent 日期解析错，修路由/描述；Harness 改参，修参数传递；工具收到正确参数却查询错误数据，才修工具实现；返回包装或最终解释错误，则修对应层。无论最终责任在哪，都要将该失败固化为回归样本。

</details>

## 跨领域同构

- **支付系统**：支付接口返回“请求已接受”不等于扣款正确；必须同时验证金额、收款人、幂等、授权和最终账务状态。支付系统通常先过未授权扣款等硬门槛，再比较延迟和吞吐。
- **数据管道**：任务进程退出码为 0 不等于数据质量正确；还要检查行数、主键唯一性、日期覆盖、字段范围和来源血缘。Agent 工具的“调用成功率”与数据管道的“程序成功退出”同构。
- **量化回测**：不能只看收益率，还要检查无前视、交易日对齐、缺数、滑点和回撤等硬约束。一个高收益但有前视偏差的策略不能算好策略。

**面试挂钩**：被问“如何评估一个 Agent 工具或工作流”时，可以按“工具契约 → 类型专属断言 → 自动化不变量 → 端到端指标 → 人工校准 → 生产回归”的顺序回答，并补一句“安全违规先做硬门控，不能被平均分抵消”。
