# 消息编排边界：Harness 组织上下文，LLM 生成下一步

## 一句话先懂

`LLM`（Large Language Model，大语言模型）只根据当前收到的 `message` 序列生成下一条响应；`Harness` 决定哪些信息进入 message、工具结果如何回流、何时继续循环、哪些动作可以执行，以及什么时候把结果交给用户。Harness 不需要穷尽所有长尾语义，而应把确定性约束交给代码，把开放语义理解交给 LLM。

## 大白话解释

把 LLM 想成一个只看桌面材料的研究员：它不会直接进入仓库、数据库或电话系统。每次工作前，Harness 决定桌上放什么：用户问题、任务状态、必要证据、可用工具说明和权限提示。

研究员读完材料后会做一件事：

```text
写一段回答
或提出一个工具调用
或请求补充信息
```

但研究员提出“请把这笔数据写入系统”，不等于系统真的写入。Harness 还要检查权限、范围、审批和风险。

工具返回后，Harness 也不一定原样把全部内容倒回桌面：可以压缩、脱敏、标注来源和时点，但不能偷偷改掉原意或丢掉会改变结论的状态。

## 第一性原理推导

1. LLM 的输入是当前请求中的消息序列；它不能凭空看到没有被放入 message 的数据库、文件或历史状态。
2. LLM 的输出是概率性的下一条响应，可能是文本、澄清问题、计划或工具调用，不是已经发生的外部事实。
3. 外部状态和副作用必须由代码、工具和数据库维护；模型输出不能自动变成执行结果或权限。
4. 上下文窗口、成本和注意力有限，不能把所有历史、工具和检索结果无限注入。
5. 确定性事实、权限和契约适合代码校验；开放式长尾语义适合 LLM 理解。
6. 如果原始问题、工具返回和最终输出之间没有记录边界，错误无法定位，也可能被表达层静默升级。

因此推出：

```text
用户 / 外部事件
→ Harness 组装当前 message
→ LLM 生成下一步响应
→ Harness 解析并验证
→ Retriever / Tool / Human / Event 节点执行
→ 结果回写状态或 message
→ 继续循环，或经过输出门控后交给用户
```

## 技术映射

### Agent 的工程公式

原书使用：

```text
Agent = LLM + 上下文 + 工具
```

从工程实现角度可以写成：

```text
Agent System = LLM + Harness Code + Tools + External State
```

两者侧重点不同：第一条讲能力组成，第二条讲这些能力如何被代码组织。Harness 是连接它们的编排层、运行控制层和权限边界。

### Message 的输入输出循环

```text
messages = [system, user, ...必要状态]
                ↓
             LLM API
                ��
assistant message：文本 / 澄清 / tool_call
                ↓
             Harness
        ┌───────┴────────┐
        │                │
   继续调用工具       最终输出门控
        │                │
 tool result        用户可见答案
        ↓
追加为 tool message
        ↓
重新组装 messages，继续下一轮
```

LLM 不是“处理整个世界”，而是处理当前可见的 message，并生成下一步；Harness 负责把概率性输出放进确定性的运行约束中。

### 预处理的正确边界

对于长尾问题，Harness 不应试图穷举所有意图。它适合做低风险、可验证的提取和约束：

```text
原始用户问题保留
+ 明确日期/代码/实体的结构化旁路信息
+ 当前用户身份与权限
+ 已知会话状态
```

例如原问题中明确出现的代码、日期格式和用户权限，可以作为 `sidecar metadata`（旁路元数据）提供给 LLM；但“用户真正想研究什么”“这是不是预测问题”这类开放语义应交给 LLM 或专门的理解组件。

这是一种保真增强：

```text
原始信息不丢
+ 确定性事实显式补充
+ 语义判断交给 LLM
+ 行动权限仍由 Harness 门控
```

### 工具结果的两种回流

短小、结构稳定、无敏感字段的结果可以近似原样回流；大型、敏感或噪声多的结果需要处理：

```json
{
  "status": "ok",
  "requested_date": "2026-08-05",
  "source_date": "2026-08-05",
  "row_count": 224,
  "summary": "...",
  "omitted_rows": 219,
  "provenance": "..."
}
```

处理后的结果应尽量保留：来源、时间、状态、完整性、降级原因和缺口。否则“降噪”可能变成“静默丢证据”。

### Node 的统一抽象

Agent 图中的节点可以抽象为：

```text
Node = 读取状态
     + 执行一个明确动作
     + 写回状态或 message
```

但不同节点的动作不同：

| Node | 输入 → 输出 | 主要动作 |
|---|---|---|
| LLM Node | message → assistant message | 语义推理与下一步生成 |
| Retrieval Node | query → evidence | 召回证据或能力候选 |
| Tool Node | tool_call → result/effect | 执行外部动作 |
| Guard Node | proposal → allow/deny | 权限和风险判断 |
| Human Node | approval request → decision | 人工确认 |
| Event Node | external event → wake-up | 唤醒或调度任务 |

这解释了为什么不能让 LLM 完全控制 Harness：LLM Node 只是整个状态机中的一个节点。

## 术语对照

- `Message`（消息）：LLM 当前一次请求能看到的结构化消息序列，包括 system、user、assistant、tool 等角色。
- `Harness`（运行时控制层）：负责消息编排、循环、工具调度、权限、状态、恢复、审计和输出门控的代码系统。
- `Context Engineering`（上下文工程）：决定给模型什么信息、如何排序、如何压缩、何时注入和何时移出。
- `Sidecar Metadata`（旁路元数据）：不替换原始用户文本、附加在旁边的结构化信息，如解析出的日期、实体和权限。
- `Progressive Disclosure`（渐进式披露）：先给摘要或目录，需要时再加载详细工具、Skill 或证据。
- `Retriever`（检索器）：被 Harness 调用的在线检索管线，不等于 Harness，也不等于单一模型。
- `Tool Call`（工具调用）：LLM 生成的结构化调用意图，不等于工具已经执行成功。
- `Output Gate`（输出门控）：在用户看到答案前检查事实边界、敏感信息和表达契约的控制点。
- `Long Tail`（长尾）：低频、表达多样、难以用少量规则覆盖的问题集合。

## 本轮场景对照

本轮对原书内容的统一理解可以表示为：

```text
用户问题
→ Harness 决定当前给 LLM 看哪些 message
→ LLM 生成文本、澄清或工具调用
→ Harness 判断是否继续、检索、调用或拒绝
→ 工具/Retriever 返回结果
→ Harness 选择原样、脱敏、压缩或结构化回流
→ LLM 继续处理 message
→ Harness 通过输出门控后交给用户
```

这里的“预处理 → 意图识别 → 路由 → 检索”可以是某个系统的工程实现模板，但不是原书规定的固定四阶段。不同系统可以：

- 原话直接交给强 LLM，再由 Harness 做结构和权限门控；
- 先做少量确定性提取，再把原话和元数据交给 LLM；
- 头部问题走规则快路径，长尾问题走模型理解；
- 由 Skill、工具目录或外部事件直接触发不同的 message 编排。

重要的是职责边界，而不是固定步骤名称。

## 替代方案与取舍

| 方案 | 优点 | 代价 |
|---|---|---|
| 原始问题直接给 LLM | 长尾灵活、少写规则、保留语义 | 成本和延迟更高，需要强输出校验 |
| Harness 规则穷举意图 | 快、稳定、可解释 | 规则膨胀，换表达就可能漏判 |
| 全部让 LLM 直接执行 | 链路短、开发快 | 结构错误、越权和副作用风险高 |
| 分层混合 | 确定性事实由代码，开放语义由 LLM，执行由 Harness | 需要明确边界、置信度和观测 |

通常更稳的是分层混合：Harness 不替代 LLM，也不把 LLM 当成权限系统。

## 边界与反例

- **Harness 不等于所有组件。** Retriever、意图解析器、Tool Executor 可以是独立组件，由 Harness 编排和约束。
- **LLM 不等于执行结果。** `tool_call` 只是提议，必须等待工具真实返回和 Harness 验证。
- **Skill 不等于授权。** 工作流文档只能提供建议，不能绕过权限门。
- **只读不等于无权限。** 公开低风险读取通常自动放行，但敏感文件、跨租户数据和不可信内容仍需限制。
- **“降噪”不等于随意删除。** 结果压缩必须保留来源、时点、状态、缺口和完整性，否则模型可能被喂到失真的上下文。
- **规则快路径不是原书硬要求。** 它是性能和稳定性优化，不能被误写成所有 Agent 的标准管线。
- **message 处理不能只看字符串。** 还要维护任务状态、外部副作用、审计和权限；不同 Node 的动作不同。

## 可复用检查清单

- [ ] LLM 当前实际看到的 message 是什么？谁组装的？
- [ ] 原始用户问题是否保留，还是被某个解析器静默改写？
- [ ] 哪些字段是确定性提取，哪些判断交给 LLM？
- [ ] tool_call 是否和真实执行结果分开记录？
- [ ] 工具结果回流前是否标注来源、时间、状态、缺口和完整性？
- [ ] 大结果是否渐进式披露、压缩或脱敏？
- [ ] Retriever、Tool Executor、Guard 是否与 Harness 职责分开？
- [ ] 长尾问题是否有交给 LLM 的退出机制，而不是继续膨胀规则？
- [ ] Skill、LLM 和检索结果是否都不能绕过 Harness 权限门？
- [ ] 最终用户输出是否经过独立门控？

## 自测题

系统遇到一个规则没有覆盖的新长尾问题。你会选择继续扩充规则、原话直接交给 LLM，还是让 LLM 直接执行？请说明完整链路。

<details>
<summary>参考答案</summary>

不应继续试图穷举所有规则，也不应让 LLM 绕过控制层直接执行。应保留原始问题，做少量确定性提取和权限注入；把原话与结构化旁路元数据交给 LLM，让它理解任务并生成检索/工具意图；Harness 再校验 Schema、权限、预算、风险和结果，允许后调用 Retriever 或 Tool；工具结果经过必要的来源、时点、长度和脱敏处理后回流 message，最终输出再过门控。

## 跨领域同构

- **编译器**：源代码是意图表达；词法、类型和权限检查由确定性组件完成；优化器可做复杂推断；生成机器码不等于程序已经在生产环境执行。
- **API 网关**：网关可以解析请求、认证、限流和审计，但业务服务负责开放语义；网关不需要理解所有业务长尾，却必须阻止未授权副作用。
- **编辑部**：记者（LLM）提出候选稿，资料室（Retriever）提供证据，主编（Harness/裁决层）决定哪些材料进入版面，最终发布前还有校对和合规门。

**面试挂钩**：被问 Agent 为什么不只是“LLM + while loop”时，可以回答：“LLM 只消费 Harness 组装的 message 并产生下一步；Harness 负责上下文、状态、工具、权限、恢复和输出门控，保证概率性模型行为不会直接变成未授权副作用。”
