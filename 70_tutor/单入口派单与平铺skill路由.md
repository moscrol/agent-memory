# 单入口派单 vs 平铺 skill 路由

## 一句话先懂

**Router（路由器）决定谁来做，Base Contract（基础答案契约）决定最低必须做到什么，Presenter（表达器）决定用户最终看到什么。** 专项 Skill（技能流程）决定高频任务的执行上限；始终生效的基础协议和统一出口决定长尾任务的质量下限。

## 大白话解释

把 Agent 想成一家医院：

- 分诊台判断患者应该去心内科、骨科还是全科，相当于 Router；
- 各专科的固定诊疗流程，相当于专项 skill；
- 所有科室都必须检查生命体征、过敏史、禁忌和危险信号，相当于 Base Contract；
- 医生综合病史、化验和影像形成判断，相当于 Adjudicator（证据裁决器）；
- 出院说明用患者能理解的语言解释结论、风险和复查时间，相当于 Presenter。

医院多开十个科室，只能扩大专科覆盖面。患者没有命中专科时，如果全科没有基础诊疗协议，最后仍可能只拿到一叠化验单。Agent 同理：增加 skill 可以提高命中后的上限，却不能自动提高未命中时的质量下限。

## 第一性原理推导

先从五个不可再简化的事实出发：

1. 用户问题是长尾分布，不可能为每一种问法都编写专项 skill。
2. Router 只做意图到执行路径的映射，不会自动创造证据、裁决冲突或组织语言。
3. 专项 skill 只在命中时增加固定检索顺序、门禁、防遗漏清单和输出骨架。
4. 检索追求少漏材料，因此候选中必然存在重复、噪声和弱相关内容；表达追求认知效率，两者目标不同。
5. 只要存在“检索结果或运行状态直接进入正文”的旁路，专项 skill 再多也不能保证长尾回答自然、清楚。

因此可以推出：

```text
用户问题
→ Router：选择执行路径和深度
→ Base Contract：所有路径都必须遵守的研究纪律
→ 可选专项 Skill：为高频任务增加固定流程
→ Adjudicator：区分事实、推断、反证和缺口
→ Answer Contract（答案语义契约）：组织本轮必须回答的语义元素
→ Presenter：转换为用户可读内容
→ Inspector：单独承载检索状态、告警和运行诊断
```

“未命中 skill”不应等于“不检索”或“裸模板”，而应进入受 Base Contract 约束的自由编排。

## 技术映射

### 三种职责不能混为一个 Router

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| Router | 判断任务类型、复杂度、执行者和权限 | 不保证证据充分，也不保证文字自然 |
| Base Contract | 规定检索前置、来源纪律、反方、缺口和最小输出义务 | 不替代专项流程 |
| 专项 Skill | 固化高频任务的查询顺序、门禁和格式 | 不可能穷举长尾问题 |
| Adjudicator | 把候选材料裁决为事实、推断、冲突或缺失 | 不负责润色 |
| Presenter | 排序、压缩、翻译和适配终端 | 不得新增事实或升级证据状态 |

### Skill 数量影响覆盖率，不直接决定可读性

需要区分三种“数量”：

1. 仓库中存在多少 `SKILL.md` 文档；
2. Runtime（运行时）实际注册了多少可调用 skill；
3. 无专项命中时，是否仍有一个始终生效的基础协议。

本轮审计中，金融仓库虽有数十个 `SKILL.md`，Workbench 对话 Runtime 实际只注册少数正式 skill。更关键的是，未命中后会回到 generic Ask；因此用户感受到的不是“文档数量少”，而是“通用路径的质量下限较低”。

### 单入口与平铺路由

- **单入口派单**：只暴露一个入口 skill，内部维护意图到 preset（权限预设）、workflow（工作流）和下游 skill 的路由；适合统一检索、来源和输出纪律。
- **平铺路由**：多个 skill 平级暴露，各自声明触发词和权限；适合边界清晰、需要显式触发的操作任务。
- **双轨制**：问答走统一入口，抓数、写库、入库等高风险操作走平铺直达。它通常比“所有任务都单入口”更安全。

## 本轮场景对照

### Workbench

本轮源码审计观察到：

- Skill Router 先靠触发词形成候选，LLM（大语言模型）只能在候选 allowlist（允许清单）中选择；
- 没有候选时进入 generic Ask（通用问答链）；
- Skill 结果通常作为补充证据再次交给通用 Ask，而不是天然拥有最终答案；
- 普通 UI 对话显式关闭长期记忆块和历史回检块；
- LLM 不可用或输出被门禁拒绝时，部分路径回退为确定性 sections，容易把证据链和运行状态直接交给用户。

Workbench 的证据治理、AnswerSpec（中间答案模型）方向和质量门禁并不弱；主要缺口是这些能力尚未成为所有路径不可绕过的统一出口。

### Knevo

根据现有逆向记录，Knevo 把 `finance-mode（金融基础模式）` 作为始终生效的操作系统层，专项 skill 只是应用层。即使未命中专项，它仍要求检索正反材料、区分记忆与当前事实、披露缺口，并按统一结论元素收敛。

这部分证据包含 Knevo 自述和行为探针，不是源码审计结论；底层模型、温度和完整系统提示词仍未知。因此合理结论是“基础协议很可能是主要架构差异”，而不是断言它是唯一原因。

## 观察、推断、预测与权限

- `observation（观察）`：Workbench Runtime 注册、路由 allowlist、记忆开关和 fallback 可从源码核对；Knevo 的部分机制来自自述与行为观察。
- `inference（推断）`：始终生效的基础协议和统一 Presenter 很可能解释了未命中专项时的可读性差距。
- `prediction（预测）`：如果 Workbench 统一 Base Contract、裁决层和 Presenter，即使不增加 skill，长尾回答也应明显改善。
- `authority（执行权限）`：上述推断不能自动授权全面重构；应先在同一模型、同一数据、同一问题集上做 A/B 评测。

事实正确不自动证明推断正确，推断合理不自动证明预测有效，预测偶尔命中也不自动授予架构替换权限。

## 替代方案与代价

| 方案 | 能解决什么 | 主要代价或盲区 |
|---|---|---|
| 继续增加专项 Skill | 提高高频任务的覆盖率和流程稳定性 | 长尾永远覆盖不完，维护和冲突成本上升 |
| 只换更强模型或加长 Prompt | 快速改善部分自然语言表现 | 属于软约束；调用失败时仍退回旧旁路 |
| 只扩大 RAG（检索增强生成）top-k | 降低漏召回概率 | 噪声更多，不会自动形成裁决和自然叙事 |
| Base Contract + Adjudicator + Presenter | 提高所有路径的质量下限 | 需要迁移旧路径，契约过硬时可能产生模板感 |
| 全面多 Agent 化 | 适合复杂并行研究 | 成本、延迟、调试和一致性风险更高 |

## 术语对照

- `Router（路由器）`：把用户意图映射到任务路径、执行深度和权限。
- `Base Contract（基础答案契约）`：所有问答路径都必须满足的最低研究与表达义务。
- `quality floor（质量下限）`：最差路径仍能保证的最低答案质量。
- `Adjudicator（证据裁决器）`：把候选材料判为事实、推断、冲突、反证或缺失。
- `Presenter（表达器）`：把已裁决内容转换成用户可读答案，不负责事实升级。
- `Inspector（运行详情面板）`：承载检索状态、内部字段、告警和调试信息。
- `allowlist（允许清单）`：Router 或模型只能从预先给定的候选集合中选择。

## 边界与反例

- Base Contract 不等于固定文案：固定的是语义义务，不是每轮机械输出相同标题。
- Presenter 只能改善表达，不能把错误证据变正确。
- 专项 skill 仍适合高频、格式敏感、需要硬门禁的任务。
- 写库、交易、发消息等高风险动作不宜完全交给模糊的单入口意图识别；应保留显式触发和最小权限，见 [[preset权限分层与最小权限]]。
- 单入口集中横切规则，也扩大了变更爆炸半径；入口协议需要版本化、回归集和灰度验证。
- 检索前置只能防“没查就答”，不能单独防止错误裁决或糟糕表达，见 [[检索前置硬触发]]。

## 可复用检查清单

- [ ] 无专项 skill 命中时，是否仍会执行检索、反方和缺口披露？
- [ ] Router 输出是否只决定路径，而不是直接决定结论？
- [ ] 召回结果是否先经过裁决，再进入用户答案？
- [ ] 有 LLM 与无 LLM 是否消费同一份语义答案契约？
- [ ] Presenter 是否只能调整表达，不能新增事实或升级状态？
- [ ] 运行诊断是否进入 Inspector，而不是占据主正文？
- [ ] 新增 skill 前，是否证明该任务高频、格式敏感或需要硬门禁？
- [ ] 写操作是否保持显式权限和可审计触发？

## 自测题

客服 Agent 只有“退款、改地址、发票”三个专项 skill。用户问未覆盖的“跨境包裹被海关退回怎么办”，但知识库中存在当前海关政策。系统应该怎样处理？

<details>
<summary>参考答案</summary>

不应直接展示搜索结果，也不必等待新增专项 skill。应进入通用服务协议：检索当前政策，区分已确认事实与待核条件，给出处理步骤、风险和升级人工的条件，再由 Presenter 生成回复。这个设计说明专项 skill 管覆盖上限，Base Contract 和 Presenter 管长尾质量下限。

</details>

## 跨领域同构

- **医院**：分诊台 → 通用诊疗规范 → 专科流程 → 出院说明。
- **客服**：意图分类 → 通用服务政策 → 专项工单流程 → 用户回复。
- **微服务**：API Gateway（应用程序接口网关，负责统一鉴权和限流）→ 领域服务；入口统一横切纪律，但不能替代领域逻辑。
- **编译器**：前端选择语法路径，中间表示保存语义约束，后端负责目标平台表达；路由不能替代中间语义。
