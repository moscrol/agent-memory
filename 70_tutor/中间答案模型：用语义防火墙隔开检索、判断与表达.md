# 中间答案模型：用语义防火墙隔开检索、判断与表达

## 一句话先懂

`AnswerSpec（中间答案模型）`不是把检索结果换成 JSON，而是在检索、判断和表达之间建立不可绕过的语义防火墙：表达层只能翻译已经裁决的主张，不能把候选线索自行升级成事实。

## 大白话解释

把研究系统想成一家新闻编辑部：

- 记者负责找线索，宁可多找一些，也不能漏掉重要材料；
- 编辑负责核实哪些线索成立、哪些冲突、哪些只能算猜测；
- 排版编辑负责把终审内容写得清楚、简洁、适合读者阅读。

如果记者把搜索结果直接交给排版编辑，排版编辑为了让文章顺畅，很容易把“有人提到过”改写成“已经发生”。即使所有内容都装进 JSON，也只是把散乱纸条换成了整齐文件夹；只要排版编辑仍能跳过终审，问题就没有解决。

AnswerSpec 相当于终审后的版面清单。它明确写出哪些是已证实事实、哪些是推断、哪些存在反证、哪些仍缺资料。Presenter 只能决定先说什么、怎么说，不能改变这些状态。

## 第一性原理推导

先从五个不可再简化的事实出发：

1. 检索追求高召回率：为了少漏信息，候选集合必然包含噪声、重复和弱相关材料。
2. 裁决追求高精确率：必须判断证据到底支持、反对、冲突还是不足，不能“搜到即成立”。
3. 表达追求认知效率：会压缩、排序和合并信息，但这种优化目标不包含事实核验。
4. 自然语言字符串会丢失类型、来源、时效和状态；下游很难再判断一句话原本是事实还是猜测。
5. 只要存在“检索结果直接进入回答”的旁路，再完善的裁决层也可能被绕过。

因此可以推出：

```text
候选证据天然含噪
→ 不能直接进入用户答案
→ 必须先形成带状态、来源和反证的 Claim
→ Claim 还要按用户问题组织成 AnswerSpec
→ Presenter 只能消费 AnswerSpec
→ 旧的字符串直通旁路必须被禁止
```

真正的分层不是代码目录里出现四个类，而是每一层的输入、输出和权限都被接口锁住。

## 技术映射

推荐的数据流：

```text
Retriever（检索器）
  → Evidence[]（候选证据）
Adjudicator（证据裁决器）
  → Claim[]（带状态的主张）
Answer Planner（答案规划器）
  → AnswerSpec（中间答案模型）
Presenter（表达器）
  → Markdown / UI / API
```

### Evidence 与 Claim 为什么要分开

`Evidence（证据）`记录原始材料是什么；`Claim（主张）`记录这些材料能支持什么结论。多个证据可以支持同一主张，同一证据也可能只支持主张的一部分。

Claim 至少需要保留：

- 主体与主张内容；
- `observation（观察事实）`、`inference（解释或推断）`、`prediction（未来预测）`等类型；
- 已证实、候选、推测、缺失、冲突等状态；
- 支持证据、反证和时效；
- 置信度及其依据。

事实正确不能自动证明推断正确，推断合理不能证明预测有效，预测偶尔命中也不能自动获得 `authority（执行或阻断权限）`。权限必须由独立门禁决定。

### AnswerSpec 应保存什么

一个通用 AnswerSpec 可以包含：

```text
summary
verified_facts
company_table
counter_evidence
gaps
triggers
next_actions
sources
system_notices
```

这些字段不是固定文案，而是用户答案的语义结构。Markdown、表格、移动端卡片和无 LLM 降级输出都可以从同一 AnswerSpec 渲染，避免不同入口各说一套。

### Presenter 可以做什么

Presenter 可以：

- 调整信息顺序；
- 合并重复项；
- 把内部术语翻译成用户语言；
- 根据终端选择表格、卡片或 Markdown。

Presenter 不可以：

- 新增 AnswerSpec 中不存在的事实；
- 把候选或推测改写成已证实；
- 删除会改变结论含义的反证和缺口；
- 自行改变决策权限。

## 替代方案与取舍

| 方案 | 优点 | 主要代价 |
|---|---|---|
| 超长 Prompt 约束 LLM | 上线最快、改动小 | 属于软约束，模型仍可能越界或遗漏 |
| 每个题材写专用模板 | 单个场景可快速稳定 | 题材越多越容易分叉，维护成本持续上升 |
| 检索结果统一 JSON 化 | 便于传输和调试 | 如果没有状态与权限边界，只是“结构化字符串” |
| Evidence → Claim → AnswerSpec → Presenter | 可审计、可复用、支持多终端和无 LLM | 前期建模和迁移成本较高，需要禁止旧旁路 |

统一 AnswerSpec 适合需要长期扩展、多题材复用和高可信输出的系统；一次性的低风险展示工具不一定需要完整四层。

## 术语对照

- `IR（Intermediate Representation，中间表示）`：连接上下游的稳定语义结构，类似编译器中的中间代码。
- `Evidence（证据）`：未经结论化的原始材料、数据行或来源记录。
- `Claim（主张）`：系统对证据完成裁决后形成的可表达判断。
- `AnswerSpec（中间答案模型）`：把已裁决主张组织成答案所需章节和状态的结构。
- `Presenter（表达器）`：把 AnswerSpec 转换成用户可读内容，不负责事实升级。
- `semantic firewall（语义防火墙）`：通过强制接口阻止未经裁决的信息跨层流动。
- `fail-open（失败后放行）`：规则失效时仍把原始内容透传出去，可能静默泄漏错误。

## 本轮场景对照

finance-workspace-private PR #210 修复了“今日复盘”落入题材分析的路由错误，并清除题材和公司图谱字段。这属于长期应保留的职责隔离。

但其中 `_humanize_daily_text` 和 `render_daily_review_answer` 仍包含过渡性路径：

```text
结构化日报
→ 中文字符串
→ 正则重新解析数字与状态
→ 生成用户结论
```

这种“结构化 → 字符串 → 再解析”的往返容易受上游措辞变化影响，也可能把业务判断阈值混入表达层。更稳定的做法是让统一架构直接从 Claim/AnswerSpec 渲染；PR #210 的字符串 humanizer 应作为止血代码，不再继续扩充，并在新 Presenter 落地后删除。

## 边界与反例

- AnswerSpec 只能减少传递过程中的变质，不能保证原始证据本身正确。
- 裁决规则可能错误；仍需来源质量、时效、反证和人工金标准。
- Schema 过度僵硬会压制长尾问题，应允许 domain pack 扩展，但不能绕过核心状态。
- 为低风险、一次性任务建立完整 Claim 图可能得不偿失，应按错误成本选择复杂度。
- “已经输出 JSON”不是分层完成的证明；关键要看 Presenter 是否仍能访问原始检索文本并自由发挥。

## 可复用检查清单

- [ ] 检索结果是否只进入 Evidence，而不是直接进入正文？
- [ ] 每个结论是否先形成带类型、状态、时效和证据引用的 Claim？
- [ ] 反证、冲突和缺失是否会保留到 AnswerSpec？
- [ ] Presenter 是否被接口禁止新增事实或升级状态？
- [ ] 无 LLM 和有 LLM 是否消费同一个 AnswerSpec？
- [ ] 是否存在字符串直通、结构化后再正则解析等旁路？
- [ ] 观察、推断、预测和执行权限是否分别验收？
- [ ] 新题材能否通过 ontology/domain pack 扩展，而不是复制整套模板？

## 自测题

医疗问答系统检索到三份材料：最新正式说明书写“禁用于孕妇”，旧医生笔记写“谨慎使用”，论坛帖子说“有人使用后没问题”。怎样分层，才能避免表达层自行降低正式约束？

<details>
<summary>参考答案</summary>

裁决层应把正式说明书记为已证实约束，把旧笔记记为时效冲突，把论坛帖子记为不足证据；AnswerSpec 保留三者状态和来源。Presenter 可以简洁表达“当前正式说明禁止使用”，但无权因为其他材料存在而把“禁止”改成“谨慎”。

</details>

## 跨领域同构

- **编译器**：词法结果不能直接生成机器码，需要 AST（抽象语法树）和 IR 保存类型、作用域与约束。
- **支付风控**：交易记录是事实，风险标签是判断，拦截动作是权限，通知文案只是表达。
- **医疗报告**：检验结果、医生诊断、预后预测和处方权限必须分开。
- **客服系统**：知识检索、政策裁决、回复规划和用户话术不能由同一个自由生成步骤完成。

这也是系统设计面试常见的 `separation of concerns（关注点分离）` 与 `typed contract（带类型契约）`：不是为了让类更多，而是为了让错误被限制在单层，便于测试、替换和追责。
