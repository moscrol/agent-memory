# 工具发现与 RAG 的同构：从检索证据到检索行动能力

## 一句话先懂

`RAG`（Retrieval-Augmented Generation，检索增强生成）检索“我应该参考什么”，工具发现检索“我应该调用什么”；两者都可以先召回可检索对象、再把候选注入上下文，但工具检索的结果可能触发外部行动，因此必须额外经过参数、权限和副作用门控。

## 大白话解释

把 Agent 想成研究助理：

- RAG 像在档案室找资料：找到公告、研报或公司说明，交给助理阅读。
- 工具发现像在工具间找设备：找到搜索器、数据库查询器或写入器，交给助理决定是否使用。

两者都不是把整座档案室或工具间全部搬到桌上，而是先根据当前任务找少量候选。

但两者的后果不同：

```text
找错一份资料：可能导致回答错误
找错一个工具：可能导致错误查询，甚至改变外部世界
```

所以工具发现可以借用 RAG 的检索技术，但不能直接照搬 RAG 的信任模型。

## 第一性原理推导

1. 文档和工具的数量都可能超过上下文能够稳定承载的规模。
2. 全量注入会增加 token 成本、干扰选择，并让模型在相似候选之间更容易混淆。
3. 因此需要先从对象集合中召回与任务相关的候选，再将少量候选放入上下文。
4. 文档候选描述“可供参考的内容”；工具候选描述“可供执行的能力”，二者的对象形态不同但召回问题同构。
5. LLM 看到候选后可以阅读证据，也可以生成结构化工具调用；后者涉及参数语义和外部副作用。
6. 相关性只能说明“可能适合”，不能说明“当前用户有权调用”，所以工具候选必须经过权限过滤和最终 Harness 门控。

因此推出：

```text
RAG：问题 → 召回证据 → 注入上下文 → LLM 解释
工具发现：问题 → 召回能力 → 注入工具定义 → LLM 选择并填参
工具执行：调用意图 → Harness 授权 → 外部动作 → 结果回流
```

## 技术映射

### RAG 与工具发现的对应关系

| RAG | 工具发现 |
|---|---|
| 公告、研报、实体页、文档片段 | 工具描述、Schema、示例和边界 |
| 文档索引 | 工具注册表/能力索引 |
| BM25、向量、混合检索、rerank | 同样可以用于工具描述召回 |
| 证据注入上下文 | 工具定义注入上下文 |
| LLM 阅读证据并回答 | LLM 选择工具并生成参数 |
| 主要产出 observation / inference | 可能产出 action |
| 通常不直接改变外部状态 | 可能读取、写入或通知外部系统 |

### Retriever 是什么

`Retriever`（检索器）不是一个固定模型，而是运行时检索管线。它可以编排：

```text
接收 query
→ 规范化
→ 调 BM25
→ 调 Embedding Model
→ 访问向量索引
→ 融合候选
→ 可选 rerank
→ 返回 Top-K
```

组件分工：

- `BGE-M3`：Embedding Model（嵌入模型），把文本编码成用于语义相似度的向量；它不是负责最终回答的聊天 LLM。
- `BM25`：关键词相关性排序算法，擅长公司名、股票代码、字段名、日期和专有词。
- `Reranker`：重排序模型，对第一阶段召回的候选做更细的相关性判断。
- `Index`（索引）：提前构建的向量、关键词和元数据检索资产。
- `Retriever`：在线查询时把上述能力组织起来的组件。

### 工具发现的一条可行管线

当工具很多时，可采用：

```text
工具注册表
→ 用户/租户/任务权限过滤
→ BM25 + 向量召回候选
→ rerank 精排
→ LLM 在 Top-K 定义中选择并填写参数
→ Harness 最终校验和执行
```

工具注册表不应只有名称，还应保存：

```text
用途、适用场景、不适用场景、参数 Schema、示例、返回契约、权限、来源、版本、延迟和成本
```

### 两阶段检索为什么合理

第一阶段追求召回：宁可保留一批候选，避免漏掉唯一合适工具；第二阶段追求精度：用 reranker 或 LLM 精细判断。它和 RAG 的“召回 Top-N → 重排序 → 注入 Top-K”同构。

但工具多出的动作是：

```text
候选定义进入 message
→ LLM 生成 tool call
→ Harness 校验参数、权限、预算和副作用
→ Tool 执行
```

## 术语对照

- `RAG（Retrieval-Augmented Generation，检索增强生成）`：先从外部资料召回证据，再让模型基于证据生成回答。
- `Tool Discovery（工具发现）`：从大量可用能力中找到与当前任务相关的工具候选。
- `Retriever（检索器）`：运行时组织索引、召回、融合和可选重排的检索组件。
- `Embedding Model（嵌入模型）`：把文本转换成向量，用于语义相似度计算。
- `BGE-M3`：可用于多语言/中文文本表示的向量模型，也能提供稀疏词权重；不是聊天式答案生成器。
- `BM25`：基于词频和词稀有度计算相关性的关键词排序算法。
- `Hybrid Retrieval（混合检索）`：组合关键词和稠密向量召回，兼顾精确词面与语义相似。
- `Reranker（重排序器）`：对初步召回的候选重新进行更精细排序的模型或组件。
- `RRF（Reciprocal Rank Fusion，倒数排名融合）`：按候选在不同召回列表中的名次融合多个排序结果。
- `Tool Schema（工具模式）`：描述工具参数类型、必填字段和约束的结构化定义。

## 本轮场景对照

原书讨论的是“数百个工具如何被发现”，不是规定某个金融项目必须使用 BGE-M3。可以把书中问题抽象为：

```text
可用工具从十几个增长到数百个
→ 全量工具定义占满上下文
→ Agent 通过工具搜索按需找到相关能力
→ 查看完整定义后再调用
```

书中还强调，MCP 互操作与工具定义是否全部常驻上下文是两个独立决策：后端可以保留 MCP 兼容，前端用工具索引、CLI 或 Skills 实现渐进式披露。

这里要保留事实边界：原书提出动态工具发现、分层组织和 Skills，但没有规定必须使用 BGE-M3、BM25 或某个小模型；具体检索器是工程实现选择。

## 替代方案与取舍

| 方案 | 优点 | 代价 |
|---|---|---|
| 全量工具定义直接注入 | 实现最简单、少一轮发现 | 上下文膨胀、选择过载、工具相似时易错 |
| 规则/标签过滤 | 快、可解释、易做权限门 | 同义表达和长尾语义覆盖弱 |
| BM25 工具检索 | 精确匹配字段、代码、工具名 | 对自然语言同义表达较弱 |
| 向量工具检索 | 处理语义相似任务 | 可能召回口径相近但权限/能力不对的工具 |
| Hybrid + rerank + LLM | 兼顾召回、精度和语义判断 | 组件更多，延迟、成本和评测复杂度上升 |

工具很少时，全量注入可能是最合理的；工具规模变大后，动态发现才更有价值。

## 边界与反例

- **工具检索不是 RAG 的完全复制。** 工具定义被注入后，LLM 可能生成外部行动，必须增加权限和副作用门控。
- **相关性不等于权限。** 最相关的工具也可能属于另一个租户、需要更高权限或不适合当前风险等级。
- **BGE-M3 不是 Retriever。** 它只是 Retriever 可以调用的向量编码器之一。
- **BM25 不是模型。** 它是关键词排序算法；Embedding 和 Reranker 才可能是模型。
- **RAG 不是没有 LLM。** RAG 通常用向量模型/关键词算法做召回，再由回答 LLM 阅读证据；工具发现还要生成结构化调用和参数。
- **当前 Skill 路由不等于独立 Tool Retriever。** 一个系统可以用触发词和 LLM 注册表选择 Skill，而没有 BGE-M3 + BM25 的工具能力索引。
- **工具发现本身也是能力。** 它需要权限、来源、版本、描述投毒和审计治理。

## 可复用检查清单

- [ ] 我检索的是证据、Skill 还是可执行能力？
- [ ] 索引里是否同时保存名称、描述、边界、Schema、权限和来源？
- [ ] 是否先做权限/租户过滤，再做相关性召回？
- [ ] 精确代码、字段和专有词是否有 BM25 或等价精确通道？
- [ ] 同义表达是否有向量召回或查询改写？
- [ ] 是否把召回 Top-N 和最终注入 Top-K 分开？
- [ ] LLM 选择候选后，是否仍经过 Harness 授权？
- [ ] 是否记录检索方式、候选、最终选择、失败和延迟？
- [ ] 工具定义本身是否经过来源和提示注入审查？

## 自测题

一个系统有 500 个工具。用户提出一个新任务，系统用向量检索召回了三个工具，其中最相关的一个需要写数据库，当前用户只有只读权限。系统应该怎样处理？

<details>
<summary>参考答案</summary>

向量相关性只表示这个工具可能适合任务，不能授予权限。系统应在工具发现阶段或调用前做权限过滤，优先向 LLM 提供当前可用的只读候选；如果任务确实需要写入，应明确告诉用户缺少权限或进入审批流程。不能因为它是 Top-1 就直接执行写操作。

</details>

## 跨领域同构

- **图书馆检索 vs 仓库领工具**：图书检索找到可参考的书；工具检索找到可执行的设备，后者还要检查领用权限和安全操作证书。
- **搜索结果 vs 可执行链接**：普通搜索结果通常需要人阅读后决定；可执行链接可能触发支付、删除或授权，因此必须多一道确认与权限门。
- **编译器链接器**：符号搜索可以找到候选实现，但链接成功不等于运行时拥有访问设备或文件的权限。

**面试挂钩**：被问“如何支持上百个 Agent 工具”时，可以回答“工具目录化、权限先过滤、Hybrid 召回、候选精排、LLM 在 Top-K 中选择、Harness 最终授权”，并说明 MCP 解决互操作而不是工具发现本身。
