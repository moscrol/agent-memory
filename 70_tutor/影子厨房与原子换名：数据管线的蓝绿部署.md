# 影子厨房与原子换名：数据管线的蓝绿部署

## 一句话先懂
- 写数据永远在"影子库"里折腾，全部写完才用一次原子改名瞬间替换生产库——客人（读请求）永远只看到"旧店"或"新店"，永远看不到装修一半的店。

## 大白话解释
- **笨办法的问题**：直接往营业中的数据库写今天的数据，写到一半（3000 只股票写完 1800 只）用户来查"今天创新高"——查出 1800 只里的新高，���户以为今天只有这些。**最坏的失败是错了还不报警**（错而不报 > 崩溃报错）。
- **三步走**：① 复制生产库 → 影子库（staging 副本）；② 18 个同步任务全往影子库写，砸了只砸影子；③ 全部完成 → `os.replace` 一瞬间把影子库改名成正式库。
- **为什么"一瞬间"成立**：`os.replace` 是操作系统保证的**原子操作**（atomic，不可再分的最小单位）——改名要么整个成功要么根本没发生，不存在改一半。像换店铺招牌是眨眼的事，不存在半新半旧挂三天。
- **结账三档**（rc 退出码）：
  - rc=0 全绿换牌：18 步全成功，正常营业。
  - rc=1 带伤换牌：挂了一两个不重要的步，主粮都在 → 照常营业但标 CHECK，明天留意。**感冒戴口罩上班**。
  - rc=2 闭店不换：大问题 → 影子库整个扔掉，生产库一字节没动。**食物中毒就闭店，绝不端上有毒的菜**。
- 为什么要中间档：数据完整性不是全有全无。"涨停热度缺失"和"大盘行情缺失"严重性完全不同。一刀切（任一失败就不换）会因小供应商天天宕机而天天没新数据；全放行会端上残缺数据。三档 = 把"什么程度的缺可以接受"写成显式判断。

## 技术映射
- `market_feature_store/sync/sync_daily_full.py`：`run_daily_full_staged` staging 编排；`_db.atomic_swap_into_place(staging, target)` 原子换名；注释明写"同步全程不持有生产库写锁"。
- 步骤隔离：每步 `_run_step(...)` 独立记录 name/ok/elapsed_s，单源失败不影响其他 17 步。
- 双供应商切换：`stock_source="snapshot"`（东财全市场快照，秒级）vs `"mootdx"`（通达信逐只 TCP，慢但可补历史）——按需选源。
- 工业界对应：**蓝绿部署**（blue-green deployment）——绿机房跑新版、蓝机房跑旧版，验证后流量一键切换。同一思想用在数据层。

## 术语对照
- `staging`（影子库/预发布副本）：生产库的完整复制品，供管道折腾。
- `os.replace`（原子改名）：操作系统级"要么全成要么没发生"的文件替换。
- `blue-green deployment`（蓝绿部署）：新旧两套环境并存、验证后一键切流的发布策略。
- `rc / exit code`（退出码）：程序结束时报告给调用方的结果状态数字。

## 本轮场景对照
- 本仓 daily-full 管线：18 步（行业字典/大盘总览/指数日线/涨停热度/新高/连板晋级/全A日线/主线/题材资金流…），staging-swap 计划，`swap_seconds` 计时换名。
- 用户自答验收：①"用户读的数据不全或者错乱，写入的内容都要有审查（lint）"——读侧脏读与写侧审查两侧都要；②"蓝绿部署，做完后整体替换"；③"中间态，有局部数据可以后补"。

## 边界与反例
- 影子库防的是**读侧脏读**，不防"数据本身错了"——源数据错，换名再原子也是错的库。内容正确性靠别的闸门（lint/质检/口径）。
- 复制成本随库体积线性涨：库大到复制不划算时（TB 级），要改用增量合并/分区交换（partition swap），本方案不适用。
- 两个进程同时跑 pipeline 会互相踩影子库——需要单实例锁（本仓由预检/preflight 承担）。

## 可复用检查清单
- [ ] 任何"定时批量写 + 有人读"的场景：先问读请求能不能容忍半截数据；不能 → staging + 原子换名。
- [ ] 失败策略有没有分档？还是一刀切？"局部可后补"和"整体不可信"要分开。
- [ ] 换名动作用的是不是真原子原语（os.replace / rename），而不是"删旧建新"（删完建到一半=两个都没有）。
- [ ] 每步是否独立记账（ok/elapsed），单点失败不拖垮整管道。

## 自测题
- 为什么 `os.replace` 的一瞬间能救场？它凭什么不会改一半？如果换成"先删旧库文件、再拷新库文件"会出什么事？

<details>
<summary>参考答案</summary>

- os.replace 由操作系统文件系统保证原子性：元数据层的改名动作不可分割，任何时刻文件路径要么指向旧库要么指向新库。
- "先删后拷"中间存在窗口：旧库已删、新库未拷完，此时读请求会拿到空/缺文件——正是原子换名要消灭的中间态。

</details>

## 跨领域同构
- 餐厅：营业中的店不动，装修在隔壁复制店里做完，验收后一夜换招牌。
- 剧场：新戏在彩排台排熟，首演当晚才切换正式舞台，观众永远不看见排练半成品。
- 网站发布：蓝绿/金丝雀发布，流量切换是原子动作，用户看不到"半新半旧"的页面。
